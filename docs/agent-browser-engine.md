# agent-browser pass-through

## Direct MCP commands

`bao mcp` exposes `agent_browser` and `finish_task`. Call `finish_task` before the final chat reply for every completed, failed, or cancelled browser task. A long-lived MCP connection has no conversation-turn-end event, so a final answer alone cannot release the browser.

```json
{"name":"finish_task","arguments":{"outcome":"passed","reason":"Verified the requested change on the page.","task":"Add milk"}}
{"name":"finish_task","arguments":{"outcome":"failed","reason":"The requested item was unavailable."}}
{"name":"finish_task","arguments":{"outcome":"passed","reason":"Cancelled both subscriptions.","done":["Cancelled Coix Seed","Cancelled Barley Tea"]}}
```

`task` is optional. It is a short name for the run, such as the request you carried out. Omit it when you have no task name. Bao stores a trimmed non-blank value and drops a blank one. [Runs](v1.md#install-and-run) uses that stored name in the list. `done` is optional too: at most 50 short items, one per thing the task did. The finished card lists them; without them it shows the reason and step counts. The result's text is one sentence of the outcome, the run line, then the workflow save result; the receipt is in `structuredContent`.

Use `finish_task`, not `close`, to end a task. It returns a sentence of the result, a `Run <run_id> · <status> · <link>` line, and the workflow save result in words, with the full run receipt in `structuredContent`, without stopping MCP, so the same client can start the next task. If session cleanup is still running, `finish_task` waits and applies the outcome to that same session's run only if it has no outcome yet. Once the session is fully removed, `finish_task` returns `no_session` and leaves earlier runs and saved workflows unchanged. Call `finish_task` before `close`; a late finish cannot change the status that a completed close computed. The agent's checked outcome and reason set the capture result, even after a recovered command failure. Earlier command failures stay in the receipt; workflow saving keeps its existing harmless-failure rule. An incomplete owner wait still fails with `session_closed`. Explicit task outcomes include a reason; a session ended without an outcome keeps its step-derived status without adding an outcome envelope. Do not finish while waiting for sign-in, `wait_for_owner`, or an owner confirmation. After 10 minutes without an agent command, Bao ends a non-waiting session as failed with a plain reason that the agent never finished the task. Active commands, owner waits, sign-in handoffs, and held replay confirmations do not expire. Idle cleanup honors keep-open for owned windows and only detaches from current Chrome, leaving its task tabs open. Settings Stop remains the replay heal policy; task completion neither heals nor calls a model.

`agent_browser` needs no running Bao app unless the gated [extension route](extension.md#running-chrome) is on. It accepts a native `command` and an `args` array. Each item is one CLI argument, without shell quoting. Supported commands are `open`, `snapshot`, `click`, `fill`, `press`, `scroll`, `tab`, `screenshot`, `wait_for_owner`, and `close`.

```json
{"command":"open","args":["http://127.0.0.1:8080/"]}
{"command":"snapshot","args":["-i"]}
{"command":"tab","args":["t2"]}
{"command":"fill","args":["@e1","hello"]}
{"command":"click","args":["@e2"]}
{"command":"close","args":[]}
```

A plain `snapshot` returns the whole native tree, often 5,000 to 20,000 characters on a real site. Two snapshot options keep the result short. Bao still runs the full native snapshot and records it in the run; only the text the agent gets changes.

- `find` takes `text`, `role`, or both. It returns only the lines whose accessible name or value contains `text` (any case) and whose role is `role`, each with its ref, the lines that hold it, and everything inside it, in page order. Refs and attributes are not searched. A miss says so in one line.
- `diff: true` returns only the lines added (`+`) or removed (`-`) since the session's last snapshot with the same `args`, with the unchanged lines that hold them. With no earlier snapshot for those `args`, or when the diff would not be shorter than the page, it returns the full tree with one line saying why. An unchanged page returns one line.

```json
{"command":"snapshot","args":[],"find":{"text":"Sign in","role":"button"}}
{"command":"snapshot","args":["-i"],"diff":true}
```

Both are accepted only on `snapshot`, one at a time. `click`, `fill`, and `press` results stay one sentence plus native status; the sentence names the new page when the address changed.

Bao fixes one session in a private socket directory, installed Google Chrome, and a visible window. On `open`, `browser: "bao"` (the default, **Bao profile**) uses Bao's separate lasting agent profile, imports site sign-ins from one of the owner's Chrome profiles, and keeps sign-ins and site data between runs. `browser: "copy"` (**Fresh Chrome copy**) starts a fresh marked copy of that Chrome profile. `browser: "current"` explicitly uses the owner's running Chrome on that profile, as described below. Close the session before changing browser or profile.

### Choose the Chrome profile

The first `open` names the Chrome profile folder with `profile`, such as `"Default"` or `"Profile 2"`. Bao lists the `Default` and `Profile N` folders in Chrome's user-data-dir, with display names and account emails from Chrome's `Local State`. When Chrome has one profile, Bao uses it and says so. When Chrome has more than one and the call names none, Bao opens nothing and records no run. The result's sentence lists every profile with its folder, name, and email, marks the one picked in Bao Settings, and the next text block gives the exact call to retry. `structuredContent` has status `needs_profile`, not an owner wait, with the sentence as `summary`, the call as `retry`, and the same profiles. A folder Chrome does not have is an error that lists the valid ones. Bao never falls back to `Default` on its own.

```json
{"command":"open","args":["https://www.nytimes.com/"],"browser":"bao","profile":"Default"}
```

Every `open` result has a `Browser:` text block after the native output. It names the route (Bao profile, Chrome copy, Running Chrome over remote debugging, or the gated extension), the Chrome app path, the user-data-dir, and the Chrome profile folder with its name and email, and says why each was chosen: the default, named by the agent, the only profile, or the fallback after a sign-in wall. The Library run stores the same facts in its `browser` field. On a Bao-profile session, each sign-in import adds a `Sign-in import` block: the site, the Chrome profile, how many of the site's cookies Bao read, and how many cookies and storage items it wrote into its profile, or why it could not read the Chrome profile. The run keeps each import in `signInImports`. Every later result in the session, including `finish_task`, ends with one short line that names the route and Chrome profile, such as `Browser: Bao profile, Chrome profile "Default".` An open that fails names what Bao tried, after the error: the route, why, the Chrome app path, and the profile folder.

On macOS 27 and later, reading Chrome's folder needs System Settings > Privacy & Security > Files & Folders > (app) > Google Chrome; [What Bao asks permission for](permissions.md#files--folders--google-chrome) says which app. Without it, every read Bao makes there fails with one message that names the switch and the app, such as `macOS did not let Bao read Google Chrome's folder (EPERM on ~/Library/Application Support/Google/Chrome). Turn on System Settings > Privacy & Security > Files & Folders > Bao > Google Chrome, then try again.` The Bao profile still opens: its `Browser:` line says `Bao imports no sign-ins:` with that message, and a refused cookie file shows the same message in the `Sign-in import` block. A Chrome copy and Running Chrome stop with it. Running Chrome checks the folder before the helper touches Chrome, and a refused `DevToolsActivePort` is reported as refused, not as `Chrome did not open its debugging port`.

```text
Browser: Bao profile, the default. Chrome app: /Applications/Google Chrome.app/Contents/MacOS/Google Chrome. User data: <Bao home>/agent-browser-profile. Sign-ins come from Chrome profile "Default" (Alex, alex@example.com) in ~/Library/Application Support/Google/Chrome, named by the agent.
```

When a Bao-profile session stops at a sign-in or human check, Bao moves it to the owner's running Chrome over remote debugging by itself, on the Chrome profile its sign-in import read. The owner's running Chrome holds his own sign-in and is a device the site already knows. Bao moves when an open or later command lands on a sign-in or check URL or title, when a snapshot shows a sign-in wall drawn in the page, and when the agent calls `wait_for_owner`. A wall in the page is a dialog with sign-in or verification wording and a password field, a code field, or a send-a-code control inside it, or a main heading with that wording and such a control on the page; `desktop/src/cdp-live/page-wall.ts` holds the rule. Bao opens the same page in a task tab of that profile, keeps the same session and Library run, and closes its own window. A snapshot that found the wall returns a new snapshot of the task tab; other commands return the task tab's open output, and the agent takes a fresh snapshot before it acts. The result says so in one line, such as `Bao's own browser hit a sign-in or verification prompt on www.nytimes.com; continued in your running Chrome (Chrome profile "Default", Alex) over remote debugging.`, followed by the full `Browser:` line of the new route. Bao tries once per session. When Chrome is not running, remote debugging is refused, or the profile window does not open, the line says why and the owner wait stays in Bao's window. A wait in Running Chrome is a real wait. When a copy session stops for a sign-in or check, the wait instruction names the fallback instead: close this session, then open the same site with `browser: "current"` on the same Chrome profile; a copy does not switch on its own. When the last session ended while a copy waited for the owner, the next `browser: "current"` open's `Browser:` line says it is the fallback after a sign-in wall. The page-engine choice does not affect this tool. For copied and Bao-owned profiles, extensions stay disabled and Bao launches Chrome itself. The current route leaves the running browser's extensions unchanged. Bao attaches the pinned native agent-browser through `--cdp`.

For copied and Bao-owned profiles, Bao picks a nonzero debugging port. Port zero makes headed Chrome set `navigator.webdriver` to true. Bao accepts only the WebSocket endpoint its own Chrome child prints to stderr, then writes that endpoint to the owned profile's `DevToolsActivePort` file. A port-bind race stops startup rather than attaching to another browser. The current route reads the running Chrome's `DevToolsActivePort` and accepts it only when the listener PID matches the selected Chrome process.

Pass-through startup connects only to Chrome's browser-level CDP endpoint and discovers targets without attaching Playwright to restored tabs. An unrelated unresponsive renderer does not block startup. Bao leaves those tabs in place without waiting for page readiness or parking startup pages. Successful `open` adds native `tab list` output. For `browser: "copy"`, the agent selects the signed-in copied tab with `tab <id>`; Bao does not guess its login state. `tab list --json` exposes CDP target ids.

`desktop/test/unit/agent-browser-startup.test.ts` covers startup with a stalled restored renderer. `desktop/test/unit/chrome-startup.test.ts` covers launch flags, a stale endpoint file, a port-bind race, browser-only startup commands, and headed `navigator.webdriver` before and after a Runtime-domain attach.

Every call's first text block is one sentence of what the step did, such as `Went to https://example.com/ ("Example")` or `Clicked "Save" (button)`. The quoted name comes from the latest snapshot line for the ref. Native stdout and stderr follow as separate MCP text blocks; a snapshot with `find` or `diff` gives Bao's shorter view of its stdout instead. Sign-in and human-check handoffs follow the sentence with Bao's wait status instead. Without MCP Apps, that status is a `Run <run_id> · <outcome>` line and the instruction in words, and `structuredContent` carries the `outcome` and `instruction`. [Browser tool cards](mcp-viewer.md#browser-tool-cards) describes the visual result and receipt handoff in MCP Apps hosts. A native failure sets `isError` and leaves the session available unless the command is `close`, which attempts cleanup even after a native failure. Bao does not block final clicks. Closing a successful, representable single-document task saves a replayable workflow. The closing result gives its workflow id or one line explaining why it was not saved. A saved file that is not [schema v4](workflow-schema.md) is not loaded.

### Workflow reuse

Successful tasks using `open`, `click`, `fill`, and `press` save a `WorkflowV2` in Workflows when the session finishes. Bao observes the actual DOM control during each action, saves its identity and locators, and records observed effects through the existing v1 trail contract. Snapshot refs such as `@e280` remain only in the raw capture. Field values become the existing workflow inputs. Snapshots and screenshots remain evidence, not replay actions. A settling-only check is low-confidence, not proof of the task's business result.

A second tab, popup, scroll, unsupported command options, an unaddressable target, a failed action that changed the page, or a failed or unfinished task leaves a capture only. Selecting the active tab, a failed read-only command, a harmless action failure followed by a successful action, and a completed owner handoff do not block saving. Handoffs stay out of the replay steps; replay uses its existing sign-in handling. Bao does not silently remove unsupported actions to save a partial workflow. The final tool result says `Saved workflow` with its id or `Not saved as a workflow` with the reason. Do not claim a workflow exists without that saved result.

Saved workflows run through the current replay engine using app Replay or MCP `run_workflow`, not through native pass-through replay. Both accept the same `browser` choice, with **Bao profile** marked as the default in the app's Run picker. In the app, that choice uses Bao's own `<Bao home>/chrome-profile` with Login sites and the saved-login gate, as do Guide, capture, Sign in, import, and recheck. Agents use the separate lasting agent profile described below. The profiles use different keychains; sign-ins made in one do not appear in the other. **Fresh Chrome copy** starts a new copy for each workflow run. Replay omits only the copy's saved-tab files, keeping cookies and site storage; agent copy sessions still restore saved tabs. `run_workflow` takes an optional `profile`, the Chrome profile folder, which wins over the Settings pick. Without it, `run_workflow` and app Replay use the profile picked in Settings, or the only one. With several and none named or picked, `run_workflow` opens nothing and fails with the profiles, their names and emails, and the exact call to retry; app Replay asks the owner to pick one in Settings. On **Bao profile**, a Chrome whose profiles Bao cannot list runs with no sign-in import and says why. A `run_workflow` result that opened a browser lists in its `browser` array the same facts as the `agent_browser` `Browser:` block: the route, the Chrome app path, the user-data-dir, the Chrome profile, why Bao chose each, and each sign-in import, including the import Bao retries at a login wall on the start page. An open that fails names what Bao tried, and a resumed held run names the route and profile in one line. When a Bao profile or copy stops at a sign-in or check, `browser` also gives the exact `run_workflow` calls that fall back to `browser: "current"` on the same Chrome profile, unless the workflow has a file step that Running Chrome refuses. Bao does not switch routes on its own. App Replay shows none of these lines. **Running Chrome** opens a new task tab with focus emulation in a window of that profile, in the background when it is the profile the owner used last, so the owner's active tab and window focus stay as they were. Replay attaches only to that tab, so the owner's other tabs stay untouched, and a tab that never answers cannot stall the start. When `run_workflow` or app Replay holds for sign-in, a confirm, or a human check, Bao brings that tab to the front. The run's tab closes when the run ends, unless the run holds for the owner. Replay leaves the owner's browser open when it disconnects. Capture receipts, raw commands, and pictures stay in their original capture run; saving does not mark that capture as a replay or establish a green replay.

### Lasting Bao profile

```json
{"command":"open","args":["https://claude.ai/"],"browser":"bao"}
```

Bao stores the agent profile at `<Bao home>/agent-browser-profile`. It keeps cookies and site data after `close` and agent exit. It uses Chrome's mock keychain so a background agent can read its saved cookies without OS Keychain access. The app keeps `<Bao home>/chrome-profile` on the OS keychain. Bao does not rename, merge, or migrate either profile.

For cookie import, Bao copies the selected Chrome source's cookie database into a temporary browser profile, reads that site's cookies through CDP, and reuses the login importer's cookie and storage helpers. It does not copy or restore source tabs. The temporary Chrome runs with `--no-startup-window`, so it opens no window; on macOS it also launches without activating the app. It stays non-headless to retain OS Keychain access and closes after import. The lasting Bao browser still opens its visible window. Every explicit open checks the selected source again, including startup. Cookies merge by name, domain, path, and partition: a source cookie replaces Bao's cookie only when its last-update time is later. Bao-only cookies stay. Bao protects live cookie changes that have not reached its disk database and keeps existing localStorage values. Empty and storage-only sources skip cookie-extraction Chrome. If that open reaches a recognized sign-in wall on another origin, Bao imports that origin and retries the requested open only when the import changed state. The same open never imports an origin twice. Bot checks, later actions, and screenshot capture never trigger that retry. It never enters credentials or answers a browser or OS prompt.

IndexedDB transfer still has no passing real-browser proof. The initial site's import uses the existing disk-copy helper; later site imports into an open browser transfer cookies and localStorage only. A cookie or storage record alone does not prove the site accepts a login.

Keep-window-open also applies to this profile. The next Bao-profile session closes that kept window before reopening the same saved profile. It also reclaims a window whose owning MCP process has exited or whose explicit close is still finishing. Another active session must close before a second session can use it. Completed app copy runs keep their windows open but mark their leases retained, so the next copy session can reclaim them. App Bao runs use their own profile and do not hold an agent-profile lease.

### Use the owner's running Chrome

Set `browser` on the first `open` to choose the route. `"bao"` is the default. `"current"` (**Running Chrome**) controls the owner's own running Google Chrome and its actual signed-in profile, not a copy. Use it when a background-launched copy cannot keep the site's sign-in. Later calls inherit that choice; omit `browser` until the session ends. If the owner's Chrome connection ends unexpectedly, Bao names the ended session and requires an explicit browser choice on the next `open`, rather than silently switching browsers.

```json
{"command":"open","args":["https://example.com/"],"browser":"current","profile":"Default"}
{"command":"snapshot","args":["-i"]}
{"command":"close","args":[]}
```

This Mac-only route uses BaoOSHelper's existing Accessibility grant. The helper opens a new inspect tab, enables Chrome's debugging checkbox if needed, and presses Chrome's native debugging Allow sheets while current-Chrome commands connect, including reconnects. Sheets already present when polling starts may also be approved; Bao does not attribute each sheet to a particular connection. It does not request Automation or Screen Recording. A locked screen, missing Accessibility access, or ambiguous browser process stops startup without asking for a new grant.

Bao opens a new task tab in a window of the chosen Chrome profile before the first navigation, and never in another profile. Chrome's debugging protocol opens tabs only in its default context, the profile the owner used last. Bao reads that context's profile folder from a hidden `chrome://version` tab. When it is the chosen profile, the task tab opens in the background, so the owner's active tab and window focus stay as they were. Otherwise Bao runs the running Chrome's own executable with `--user-data-dir` and `--profile-directory`, and Chrome opens the task tab in front, in a window of that profile. If no such tab appears, Bao says so and stops. `tab new` is refused on a tab Chrome opened in front, because Chrome would put the new tab in its default context. It keeps focus emulation on for that tab, so the page paints, runs timers, and takes clicks and typing while the owner looks at another tab. Bao binds the native session to the task tab through agent-browser's session tab binding; a native daemon restart returns to that tab but loses refs, so take a fresh snapshot. A tab the agent opens with `tab new` on a background task tab comes to the front, because agent-browser has no background option. When a sign-in or human check needs the owner, Bao brings the task tab to the front. It keeps one browser-level CDP connection for metadata, page pictures, and focus emulation. Stay in the current session's task tab, which shares the owner's sign-ins; use another tab only when the owner asks. The Settings Chrome profile does not pick this route's profile for `agent_browser`; the first `open` names it. It does for `run_workflow` and app replays on Running Chrome. Both routes record commands and page screenshots in Runs.

`finish_task`, `close`, MCP disconnect, and handled stop signals close only task tabs Bao created, then detach from current Chrome. Bao tracks their target ids, including tabs the agent opened with `tab new`. Pre-existing owner tabs stay open, even if the agent selected one during the task. Bao never quits, signals, or relaunches the borrowed Chrome or removes its profile. Keep-open applies only to copied windows. [Session end](#session-end) defines native daemon shutdown and state cleanup. Bao leaves the debugging checkbox enabled; this route does not restore the old preference or revive retired live-driver workflows.

### Session end

For every route, Bao stops only this session's native daemon before removing its private state directory. It waits up to one second after each of two SIGTERM attempts, then up to one second after SIGKILL, and verifies exit. If signaling or exit verification fails, cleanup preserves the state directory; current Chrome still detaches without closing the borrowed browser. A cleanup that fails for any reason is reported once, by the call that ran it, as `Bao could not clean up the browser session of run <run_id>: <error>`. The run keeps its outcome and stores the error as `cleanupError`. Bao then lets the session go, so the next call starts fresh instead of repeating the error. Bao lists only the Chrome processes whose command line names the session's profile, so a long process list does not break open, close, or `finish_task`; when even that list cannot be read, shutdown stops the processes Bao started and keeps a Bao-profile or copy marker for the next session to reclaim.

For the copied-profile route, `finish_task` closes the browser by default and finalizes the existing capture without adding a native close command. `close` ends only this session and removes its copy after Chrome stops. It succeeds if the owner already closed the marked window or the session already ended. Agent exit, MCP disconnect, and SIGINT/SIGTERM/SIGHUP close the marked window, delete its copy, and finish the run by default. Proxy cleanup starts at once, even when another tool call is still waiting.

In **Settings → Technical details → Agent window**, **Keep window open after agent finishes** leaves the marked window available for a manual final step. This local choice is off by default and does not enable extensions. Bao still finishes the run and removes the native agent's private state. The next copied-profile agent session closes the kept window and deletes its copy before opening a fresh one, even if the setting has since been turned off. A kept copy stays on disk until the next agent session cleans it up, even if the owner closes its window by hand. Keep-open applies when `finish_task` ends a task, the agent disconnects, or Bao MCP stops. An explicit `close`, or closing the window by hand during a live session, still closes Chrome and deletes its copy. Bao never closes the source profile or another Bao home's window.

Kept Chrome has no Bao owner and keeps a local debugging port open, even after you close its window, until you quit that Chrome or the next agent session reclaims its copy. Other local processes, including those run by another OS user, can use that port to read the copy's cookies or control its signed-in pages. Bao has already finished the run and no longer records those actions.

### Wait for owner input in the same session

When the active tab's URL or title signals sign-in, a verification code, Imperva, or hCaptcha, Bao returns `outcome: "halted"`. It keeps that tab, browser session, MCP process, and Library run. The page shows a **Bao is waiting for you** banner, and the Library run says **needs you**. The owner signs in or clears the check in that tab.

```json
{"command":"wait_for_owner","args":["60000"]}
```

The optional timeout is 1 to 120000 milliseconds, with a default of 60000. It limits each check, not the whole owner wait. The run viewer labels the step **Wait for you to sign in or clear a check**, with the limit in seconds or minutes. Without an explicit run deadline, the wait status says **no overall timeout**. Each call stays below the 180-second MCP limit. On `waiting`, call it again without ending the agent turn. Temporary metadata or CDP errors keep the handoff open until the call's deadline. On `ready`, take a fresh snapshot and continue in the same session. On `closed`, report the returned session-ended instruction. If the owner's Chrome session ended unexpectedly, reconnect with `open` and `browser: "current"` or explicitly choose `browser: "bao"` or `browser: "copy"`; do not silently switch browsers. Do not start another MCP process to resume this window. Closing during an owner wait finalizes its run as `failed` with reason `session_closed` and records the running wait step as failed.

During handoff, Bao polls only the pinned tab's URL and title through browser-level CDP. It does not run native page commands, inspect fields, read text, take snapshots, or save screenshots. Other page commands return the handoff without recording their arguments. `close` and `finish_task` stay available to end an abandoned task; ending an unfinished handoff records a failed run with reason `session_closed`. `wait_for_owner` never forwards a native command or saves a page picture.

Only `wait_for_owner` continues an owner wait. Claude Desktop keeps one Bao MCP process across chats, so a new chat's `open` would otherwise land on an older chat's wait. An `open` during an owner wait ends that wait and its session, then starts a new task. An owner wait that no `wait_for_owner` call continues ends 30 minutes after it started or the latest `wait_for_owner` call returned (`OWNER_WAIT_LIMIT_MS` in `desktop/src/cdp-live/owner-wait.ts`). Bao never ends a wait the agent keeps continuing, so the owner can take as long as he needs, for example to type a code a site emailed. A timer does this, and every `agent_browser` call first checks the limit too, because timers do not run while the Mac sleeps. Either way Bao ends the session as if it were closed: its run finishes `failed` with reason `session_closed`, and the window or task tab closes. The next result gives one line, such as `Bao ended an earlier owner wait from 10:59 PM (run <run_id>); a new open starts a new task.` or `...; nobody continued it for 30 minutes.`

The wait sentence, banner, and instruction name what the page asks, from its title first, then its address: sign in, or clear a human check. A page Bao does not recognize, or one whose title asks to confirm or verify an account or enter a code, gets neutral words: finish the check on the site. Bao never calls such a page a sign-in. The wait time reads in words, such as `waiting 4 min` or `waiting 9 h 53 min`.

Readiness means the tab has an HTTP(S) URL and a nonblank title, its URL or title changed, neither matches a sign-in/check marker, and both stayed stable for 750 milliseconds. This is not proof of authentication. An unchanged URL and title keep waiting even if page content changes. An unrecognized check can use `wait_for_owner` to enter the same private wait; on a Bao-profile session Bao first tries Running Chrome. Metadata does not identify every sign-in form or embedded challenge.

## Pick an engine and profile

The **Settings → Technical details → Page engine** choice remains separate from `agent_browser`. Under **agent-browser (trial)**, saved workflows that explicitly declare `driver: "playwright"`, including supported pass-through tasks, remain searchable and replay through the same browser path as **Current engine (default)**. Other workflows still return `pass-through sessions do not support saved workflow replay`. Historical live workflows remain retired under either choice; see [retirement behavior](cdp-live.md).

Settings → Technical details → Page engine → **Chrome profile** lists existing `Default` and `Profile N` directories under either engine. Chrome's `Local State` supplies display names and account emails. Missing names fall back to the directory name; missing directories are omitted. The saved `chromeProfile` choice selects the source for MCP workflow runs and app **Fresh Chrome copy** and **Running Chrome** runs. Pass-through sessions take the folder from `profile` on the first `open`; the Settings choice is only marked in the list Bao returns when Chrome has several profiles and the open names none. See [Choose the Chrome profile](#choose-the-chrome-profile). App **Bao profile** runs use Login sites instead; see [Workflow reuse](#workflow-reuse).

The copied-profile route reads the selected source and creates a private copy outside the checkout. It does not launch, write to, or lock the source profile. Only the Chrome child gets the real HOME from the passwd entry so it can use the login keychain. The native command process keeps a private HOME. No remote-debugging toggle, Accessibility, Automation, or Screen Recording grant is needed. If a permission prompt appears, stop rather than approving it to keep a test running.

The copy keeps cookies, saved tabs, session-restore files, Session Storage, and encryption metadata. Cache directories are omitted. Chrome starts with sync off and `--restore-last-session`. Bao changes only the copy's exit marker, profile name, theme, avatar, and new-tab background. The profile name is **Bao copy of <original name>**. Its light orange or blue theme differs from the source; its avatar is the origami fox, or penguin when the source already uses the fox. Extensions stay off, including copied themes. These markers do not prove every site's login survives copying.

The copy has mode `0700`. Copying stops after five minutes or 20 GiB. Bao refuses links and active copies. [Session end](#session-end) defines window and copy cleanup. A released keep-open copy or a copy whose Bao process has exited can be reclaimed: Bao stops only Chrome processes using that exact marked directory before deleting it, never the source profile. The 10-minute inactivity backstop does not close a session during an active command or owner wait.

## Known gaps

Running Chrome through the Bao extension is gated off. Set `"runningChromeExtension": true` in the Library's `settings.json` to use it instead of remote debugging; no screen offers it. [Running Chrome](extension.md#running-chrome) describes that route. It runs in the Chrome profile where the extension is linked and takes no `profile`.

During current-route connections and native commands, `debug-allow` polling calls `app_from_pid(pid, true)` and `child_list`, which set `AXManualAccessibility` and `AXEnhancedUserInterface` on Chrome's accessibility elements. ## Evidence

Each session creates one `kind: "capture"` run in the Library home Bao.app reads. See [Runs and Detailed evidence](v1.md#install-and-run) for the desktop controls that expose commands, screenshots, and native output. The capture receipt remains recording-only, with no replay or teaching actions; a separately saved workflow appears in Workflows. The capture omits Identity and Snapshot inspectors. Durable replay identities and observed effects live in the saved workflow's trail. Capture runs do not claim to count the outside agent's model calls or establish replay green status.

Each step stores its exact command and argv, native stdout/stderr and exit codes, error flag, start/end times, and its sentence (`summary`). Bao saves a pending `open` before startup and updates the run atomically as results arrive. Startup failure produces a failed run with its original error and no invented picture. Uncatchable process termination can leave readable partial runs marked `recording`; handled stops finish the run as described in [Session end](#session-end).

Bao takes a separate page screenshot through CDP on the active tab after each ordinary command, with a three-second deadline. Owner handoffs and every `wait_for_owner` call omit page pictures and native screenshot copies. This does not change native refs or screenshot history. Native screenshot files, including relative and default paths, are copied into `shots/runs/<runId>/` before the private state directory disappears. After `close`, the step records the missing page rather than reusing a picture. A recording or screenshot failure logs a warning without changing native command forwarding.

**Raw command arguments, results, and screenshots can contain credentials. This route does not redact them. Do not send data you do not want saved locally.** Saved-workflow input persistence is a separate contract in [permissions](permissions.md#secret-text-in-saved-files).
