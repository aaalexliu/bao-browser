# agent-browser pass-through

## Direct MCP commands

`bao mcp` exposes `agent_browser` and `finish_task`. Call `finish_task` before the final chat reply for every completed, failed, or cancelled browser task. A long-lived MCP connection has no conversation-turn-end event, so a final answer alone cannot release the browser.

```json
{"name":"finish_task","arguments":{"run_id":"run-...","outcome":"passed","reason":"Verified the requested change on the page.","task":"Add milk"}}
{"name":"finish_task","arguments":{"run_id":"run-...","outcome":"failed","reason":"The requested item was unavailable."}}
{"name":"finish_task","arguments":{"run_id":"run-...","outcome":"passed","reason":"Cancelled both subscriptions.","done":["Cancelled Coix Seed","Cancelled Barley Tea"]}}
```

`run_id` is the run id the chat's latest `agent_browser` result names. While a session is open, `finish_task` needs it and ends only that run's session; [Wait for owner input in the same session](#wait-for-owner-input-in-the-same-session) says why and gives the replies.

`task` is optional. It is a short name for the run, such as the request you carried out. Omit it when you have no task name. Bao stores a trimmed non-blank value and drops a blank one. [Runs](v1.md#install-and-run) uses that stored name in the list. `done` is optional too: at most 50 short items, one per thing the task did. The finished card lists them; without them it shows the reason and step counts. The result's text is one sentence of the outcome, the run line, the ended-wait line when [an owner wait Bao ended](#wait-for-owner-input-in-the-same-session) still has one, then the workflow save result. `structuredContent` is a short receipt for the model: that sentence, the run id, status, link, workflow line, `endedWait` when that line is present, and browser lines. It does not repeat each step's native output. Call `get_run` for the saved receipt. The finished card shows the task name, the outcome sentence, the done list when one was sent, and the step counts.

Use `finish_task`, not `close`, to end a task. The result above does not stop MCP, so the same client can start the next task. If session cleanup is still running, `finish_task` waits and applies the outcome to that same session's run only if it has no outcome yet. Once the session is fully removed, `finish_task` returns `no_session` and leaves earlier runs and saved workflows unchanged. Call `finish_task` before `close`; a late finish cannot change the status that a completed close computed. The agent's checked outcome and reason set the capture result, even after a recovered command failure. Earlier command failures stay in the receipt; workflow saving keeps its existing harmless-failure rule. An owner wait that is still open still fails with `session_closed`. [Wait for owner input in the same session](#wait-for-owner-input-in-the-same-session) says when that call's deadline has already ended the wait, so `finish_task` then records the caller's outcome. Explicit task outcomes include a reason; a session ended without an outcome keeps its step-derived status without adding an outcome envelope. Do not finish while waiting for sign-in, `wait_for_owner`, or an owner confirmation. After 10 minutes without an agent command, Bao ends a non-waiting session as failed with a plain reason that the agent never finished the task. Active commands, owner waits, sign-in handoffs, and held replay confirmations do not expire. Idle cleanup honors keep-open for owned windows and only detaches from current Chrome, leaving its task tabs open. Settings Stop remains the replay heal policy; task completion neither heals nor calls a model.

`agent_browser` needs no running Bao app unless the gated [extension route](extension.md#running-chrome) is on. It accepts a native `command` and an `args` array. Each item is one CLI argument, without shell quoting. Supported commands are `open`, `snapshot`, `click`, `fill`, `press`, `scroll`, `tab`, `screenshot`, `wait_for_owner`, and `close`.

```json
{"command":"open","args":["http://127.0.0.1:8080/"]}
{"command":"snapshot","args":["-i"],"run_id":"run-..."}
{"command":"tab","args":["t2"],"run_id":"run-..."}
{"command":"fill","args":["@e1","hello"],"run_id":"run-..."}
{"command":"click","args":["@e2"],"run_id":"run-..."}
{"command":"close","args":[],"run_id":"run-..."}
```

Pass `run_id` on every command except a new `open` while a session is open. Pass it on `open` when continuing your own task. An `open` with no `run_id` starts a new task and ends any other open task. An `open` that names a run a newer task ended does not start a new task and does not touch the open session. An `open` with a stale run id that is not a run a newer task ended still ends the open run and starts a new task.

A plain `snapshot` returns the whole native tree, often 5,000 to 20,000 characters on a real site. Two snapshot options keep the result short. Bao still runs the full native snapshot and records it in the run; only the text the agent gets changes.

- `find` takes `text`, `role`, or both. It returns only the lines whose accessible name or value contains `text` (any case) and whose role is `role`, each with its ref, the lines that hold it, and everything inside it, in page order. Refs and attributes are not searched. A miss says so in one line.
- `diff: true` returns only the lines added (`+`) or removed (`-`) since the session's last snapshot with the same `args`, with the unchanged lines that hold them. With no earlier snapshot for those `args`, when most of the page changed, when the changed part is too large to compare, or when the changed lines are longer than the full tree, it returns the full tree with one line saying why. A few changed lines on a tiny page stay a diff, even when that list is not shorter than the page. An unchanged page returns one line.

```json
{"command":"snapshot","args":[],"find":{"text":"Sign in","role":"button"},"run_id":"run-..."}
{"command":"snapshot","args":["-i"],"diff":true,"run_id":"run-..."}
```

Both are accepted only on `snapshot`, one at a time. `click`, `fill`, and `press` results stay one sentence plus native status, then the picture line the [host contract](mcp-viewer.md#host-contract) names when it applies. The sentence names the new page when the address changed.

Bao fixes one session in a private socket directory, installed Google Chrome, and a visible window. On the Bao profile and copy routes that window stays behind the owner's apps; see [Keep Bao's Chrome behind](#keep-baos-chrome-behind). On `open`, `browser: "current"` (the default, **Running Chrome**) uses the owner's own running Chrome on one of his Chrome profiles, with the sign-ins he already has, as described below. `browser: "bao"` (**Bao profile**) uses Bao's separate lasting agent profile, imports site sign-ins from that Chrome profile, and keeps sign-ins and site data between runs. `browser: "copy"` (**Fresh Chrome copy**) starts a fresh marked copy of that Chrome profile. Bao uses a copy only when the agent names it. It uses the Bao profile when the agent names it, when a workflow moves files, and when an open that named no browser cannot use running Chrome. Close the session before changing browser or profile.

#### Sites that stay in running Chrome

Some sites tie their sign-in to the owner's own Chrome. Google binds its session to a key on his Mac (device-bound sessions), so a copied Google sign-in used in another browser signs him out everywhere. The Times counts each browser that holds its session as one more device and asks for a code. So Bao opens these sites in the owner's running Chrome:

- Google: `google.com` and its subdomains, Google's country sites such as `google.co.uk`, and `youtube.com`.
- `nytimes.com` and its subdomains.
- Any site listed in the Chrome profile's `Device Bound Sessions` table. Bao reads only the table's `key` column, one site per row.

A first `open` of such a site goes straight to running Chrome on the same Chrome profile, even when it names `browser: "bao"` or `browser: "copy"`. When the Bao extension is the running-Chrome route, that open goes through the extension instead. Two cases stay out: a workflow with a download or upload step runs on the browser it names, and when the remote-debugging open fails an open that named no browser opens the Bao profile with no sign-in import, an open that named `browser: "bao"` opens that profile and imports the other sites, and an open that named `browser: "copy"` opens the copy. The extension route has no such fallback. The running-Chrome `Browser:` line gives the reason `this site ties its sign-in to your Chrome`. A fallback line gives `fallback when running Chrome could not be used`, and a named Bao profile or copy also says why running Chrome failed. `run_workflow` follows that same first open and named fallback. A LaunchServices stall stops that launch instead, as [Keep Bao's Chrome behind](#keep-baos-chrome-behind) describes. A later `open` of such a site in a Bao-profile or copy session moves the session to running Chrome before any import, with the line `Bao did not open www.nytimes.com in its own browser because this site ties its sign-in to your Chrome; continued in your running Chrome (Chrome profile "Default", Alex) over remote debugging. Take a fresh snapshot before acting.` A sign-in wall on such a site in a Bao-profile session imports nothing and moves to running Chrome the same way. A copy does not move at a sign-in wall; it moves only when the open is one of these sites. See [Known gaps](#known-gaps) for the cases left on purpose.

Bao never writes a Google sign-in cookie (`SID`, `HSID`, `SSID`, `APISID`, `SAPISID`, `SIDCC`, `LSID`, `OSID`, `LOGIN_INFO`, and the `__Secure-` and `__Host-` forms of them) into a profile it owns, whatever the site, including the app's Login sites profile. It also never writes a Times cookie, nor a cookie of a site in the `Device Bound Sessions` table of the Chrome profile it imports from. Every Bao-owned profile, the agent's Bao profile and the app's `<Bao home>/chrome-profile` alike, loses its Google sign-in and Times cookies while its Chrome is stopped, each time Bao starts that Chrome. Every launch of a lasting Bao profile, the agent's and the app's `<Bao home>/chrome-profile` alike, also drops cookies of sites in the Device Bound Sessions table of the Chrome profile picked in Settings when that folder is present, or of every `Default` or `Profile N` folder when none is picked or that folder is missing. The app sends a default run, and a run that picked **Bao profile**, to running Chrome for Google, the Times, or a device-bound site on that same list, unless the workflow has a file step. An app Replay that names **Fresh Chrome copy** also goes to running Chrome for those sites. When that remote-debugging open fails, it opens that copy, not the app's own `<Bao home>/chrome-profile`. The extension route has no such fallback. A Bao-profile open that imports from a named Chrome profile drops that profile's device-bound sites too. A Chrome copy leaves all of these cookies and the `Device Bound Sessions` table out. A copy is also not signed in to Chrome: Bao deletes the rows of the `token_service` table in its `Web Data`, which hold the Google account's refresh token, keeps the rest of `Web Data`, such as autofill, and clears the signed-in account from its `Preferences`. The app's Login sites refuse these sites with a plain line and do not probe them; they use the owner's running Chrome instead. `bao import-login` refuses Google, YouTube, the Times, and a device-bound site in that same list or in the profile the import names, and writes no cookie of such a site. A sign-in import reads the owner's cookies in a helper Chrome that holds only the target site's cookies and cannot reach any host (`--disable-background-networking`, `--no-proxy-server`, and `--host-resolver-rules="MAP * ~NOTFOUND"`).

### Choose the Chrome profile

The first `open` names the Chrome profile folder with `profile`, such as `"Default"` or `"Profile 2"`. Bao lists the `Default` and `Profile N` folders in Chrome's user-data-dir, with display names and account emails from Chrome's `Local State`. When Chrome has one profile, Bao uses it and says so. When Chrome has more than one and the call names none, Bao opens nothing and records no run. The result's sentence lists every profile with its folder, name, and email, marks the one picked in Bao Settings, and the next text block gives the exact call to retry. `structuredContent` has status `needs_profile`, not an owner wait, with the sentence as `summary`, the call as `retry`, and the same profiles. A folder Chrome does not have is an error that lists the valid ones. Bao never falls back to `Default` on its own.

```json
{"command":"open","args":["https://www.nytimes.com/"],"browser":"bao","profile":"Default"}
```

Every `open` result has a `Browser:` text block after the native output. It names the route (Bao profile, Chrome copy, Running Chrome over remote debugging, or the gated extension), the Chrome app path, the user-data-dir, and the Chrome profile folder with its name and email, and says why each was chosen: the default, named by the agent, the only profile, the fallback after a sign-in wall, `this site ties its sign-in to your Chrome`, or the fallback when running Chrome could not be used. A named fallback from a site that ties its sign-in to Chrome also prints why running Chrome failed, on its own line, which the `browser` field does not store. The Library run stores every route it used in `routes`, each with the 1-based step it started at, and keeps the latest in `browser`. An older run stores only `browser`. On a Bao-profile session, each sign-in import adds a `Sign-in import` block: the site, the Chrome profile, how many of the site's cookies Bao read, and how many cookies and storage items it wrote into its profile, or why it could not read the Chrome profile. The run keeps each import in `signInImports`. Every later result in the session, including `finish_task`, ends with one short line that names the route and Chrome profile, such as `Browser: Bao profile, Chrome profile "Default".` An open that fails names what Bao tried, after the error: the route, why, the Chrome app path, and the profile folder. When running Chrome and its fallback both fail, that line names both routes and both reasons, once.

On macOS 27 and later, reading Chrome's folder needs System Settings > Privacy & Security > Files & Folders > (app) > Google Chrome; [What Bao asks permission for](permissions.md#files--folders--google-chrome) says which app. Without it, every read Bao makes there fails with one message that names the switch and the app, such as `macOS did not let Bao read Google Chrome's folder (EPERM on ~/Library/Application Support/Google/Chrome). Turn on System Settings > Privacy & Security > Files & Folders > Bao > Google Chrome, then try again.` The Bao profile still opens: its `Browser:` line says `Bao imports no sign-ins:` with that message, and a refused cookie file shows the same message in the `Sign-in import` block. A Chrome copy and a named Running Chrome stop with it. An `open` or run that named no browser opens the Bao profile instead, with the reason `fallback when running Chrome could not be used`. Running Chrome checks the folder before the helper touches Chrome, and a refused `DevToolsActivePort` is reported as refused, not as `Chrome did not open its debugging port`.

```text
Browser: Bao profile, named by the agent. Chrome app: /Applications/Google Chrome.app/Contents/MacOS/Google Chrome. User data: <Bao home>/agent-browser-profile. Sign-ins come from Chrome profile "Default" (Alex, alex@example.com) in ~/Library/Application Support/Google/Chrome, named by the agent.
```

When a Bao-profile session stops at a sign-in or human check, Bao moves it to the owner's running Chrome over remote debugging by itself, on the Chrome profile its sign-in import read. The owner's running Chrome holds his own sign-in and is a device the site already knows. Bao moves when an open or later command lands on a sign-in or check URL or title, when a snapshot shows a sign-in wall drawn in the page, and when the agent calls `wait_for_owner`. A wall in the page is a dialog with sign-in or verification wording and a password field, a code field, or a send-a-code control inside it, or a main heading with that wording and such a control on the page; `desktop/src/cdp-live/page-wall.ts` holds the rule. Bao opens the page the session was on before a sign-in or check address, or the page that holds an in-page dialog, in a task tab of that profile, keeps the same session and Library run, and closes its own window. An open reopens the page that open asked for, not an earlier page, except a check found only by its title, which reopens that check's own URL. A click or later navigation reopens the page before the wall when the wall matched on the URL path, a redirect to a sign-in or check address, and when a sign-in title is on a different host from that page, such as a Microsoft sign-in at `login.microsoftonline.com`. A check found only by its title, such as a Cloudflare "Just a moment" title, and a sign-in title on the same host, such as a "Sign in" title on the article URL, reopen that wall's own URL. The line names the wall's host, not the host of the page it reopens: a sign-in redirect to `accounts.example.com` says `a sign-in page on accounts.example.com` even when the reopened page is a restaurant site the agent reached by clicking. `a sign-in or verification prompt` is only for a snapshot that matched an in-page wall. A later `wait_for_owner` whose page is not a URL or title wall, including a dialog an earlier wait started, says `a step that needs the owner`, not `a sign-in or verification prompt` and not `a sign-in page`. A snapshot that found the wall returns a new snapshot of the task tab. A click, fill, press, scroll, tab, or screenshot that met the wall before it ran does not run: Bao records that step as the open it ran in the task tab and returns the open output, and the agent takes a fresh snapshot before it acts. The result's first sentence says so, such as `Bao's own browser hit a sign-in or verification prompt on www.nytimes.com; continued in your running Chrome (Chrome profile "Default", Alex) over remote debugging. Take a fresh snapshot before acting.`, and the run keeps that sentence on the step, so it shows that earlier steps ran in Bao's own browser. `routes` keeps both routes, including the Bao-profile user-data-dir and profile, each with the step it started at. The full `Browser:` line of the new route follows. When Chrome is not running, remote debugging is refused, or the profile window does not open, the line says why and the owner wait stays in Bao's window. Bao does not try again on its own, but every later `wait_for_owner` tries Running Chrome again before it waits, and waits for the time its timeout has left, but at least 5 seconds, or the whole timeout when that is shorter, so a slow failed move still leaves time to see the owner clear the wall. While the session stays in Bao's window after a failed move, halted and waiting results give the exact calls to fall back: close this session, then open that same page with `browser: "current"` on the same Chrome profile. A wait in Running Chrome is a real wait. When a copy session stops for a sign-in or check, the wait instruction names the fallback instead: close this session, then open that same page with `browser: "current"` on the same Chrome profile; a copy does not switch on its own. When the last session ended while a Bao profile or copy waited for the owner, the next `browser: "current"` open's `Browser:` line says it is the fallback after a sign-in wall. The page-engine choice does not affect this tool. For copied and Bao-owned profiles, extensions stay disabled and Bao launches Chrome itself. The current route leaves the running browser's extensions unchanged. Bao attaches the pinned native agent-browser through `--cdp`.

For copied and Bao-owned profiles, Bao picks a nonzero debugging port. Port zero makes headed Chrome set `navigator.webdriver` to true. Bao accepts only the WebSocket endpoint its own Chrome child prints to stderr, then writes that endpoint to the owned profile's `DevToolsActivePort` file. A port-bind race starts a direct Chrome again on a new port rather than attaching to another browser. The macOS open launcher is not started again. The current route reads the running Chrome's `DevToolsActivePort` and accepts it only when the listener PID matches the selected Chrome process.

Pass-through startup connects only to Chrome's browser-level CDP endpoint and discovers targets without attaching Playwright to restored tabs. An unrelated unresponsive renderer does not block startup. Bao leaves those tabs in place without waiting for page readiness or parking startup pages. On `browser: "copy"`, Bao opens a new blank background tab beside the restored tabs and binds the native session to it, so the first `open` loads there. The restored tabs stay untouched, and Bao knows the bound target. Like any tab the agent opens on this route, it opens in the background, so the copy never lifts Chrome over the owner's apps; focus emulation keeps it visible and its timers running. Bao waits up to 15 seconds for Chrome to show its first restored page before it opens that tab, so the tab joins the restored window instead of a window of its own. When Chrome shows only startup pages, such as a New Tab page, Bao binds the native session to that tab and opens no second one. Without that tab the native daemon drove the first restored tab that answered and navigated it away. Before focus emulation that tab was often hidden, and a logged-out x.com reached its load event after 3.1 to 24.4 seconds there, against the native 25-second load deadline; in a visible tab it took 0.36 to 0.43 seconds. The session's first native call starts the native daemon, which attaches to every tab and takes about 6 seconds with 20 restored tabs. Only the session's end bounds that call. A fixed tab read used to cut that start off, and the capture could not be saved as a workflow. Successful `open` adds native `tab list` output. For `browser: "copy"`, the agent can switch to a signed-in restored tab with `tab <id>`. The switch attaches to that tab and turns on focus emulation. It does not select the tab, and it does not bring Chrome forward. The tab shown in the copy window stays the one Chrome restored. Clicks, typing, and screenshots still work on the unselected tab. Bao does not guess its login state. `tab list --json` exposes CDP target ids.

`desktop/test/unit/agent-browser-startup.test.ts` covers startup with a stalled restored renderer, a copy with 20 restored tabs that opens a timer-heavy page in its own tab, keeps every restored tab, and saves the task as a workflow, and a fake native executable whose first call sleeps 6 seconds and still lets that capture save. `activePage` leaves its first tab read without a timer, so removing only the daemonStarted clear does not fail it. With both first-call guards removed, the 30 s progress ceiling bounds that read, and a 6 s sleep still passes. A first-call limit under 6 s, like the old 5 s tab read, fails it. `desktop/test/unit/chrome-startup.test.ts` covers launch flags, a stale endpoint file, a port-bind race, browser-only startup commands, and headed `navigator.webdriver` before and after a Runtime-domain attach.

Every call's first text block is one sentence of what the step did, such as `Went to https://example.com/ ("Example")` or `Clicked "Save" (button)`. The quoted name comes from the latest snapshot line for the ref. Without MCP Apps, a `Run <run_id>` line comes next. Native stdout and stderr follow as separate MCP text blocks; a snapshot with `find` or `diff` gives Bao's shorter view of its stdout instead. A picture text block can follow that output. The [host contract](mcp-viewer.md#host-contract) names when it is left out. Sign-in and human-check handoffs follow the sentence with Bao's wait status instead. Without MCP Apps, that status is a `Run <run_id> · <outcome>` line and the instruction in words, and `structuredContent` carries the `outcome`, `instruction`, and `run_id`. [Browser tool cards](mcp-viewer.md#browser-tool-cards) describes the visual result and receipt handoff in MCP Apps hosts. A native failure sets `isError` and leaves the session available unless the command is `close`, which attempts cleanup even after a native failure. Bao does not block final clicks. Closing a successful, representable single-document task saves a replayable workflow. The closing result gives its workflow id or one line explaining why it was not saved. A saved file that is not [schema v4](workflow-schema.md) is not loaded.

### Workflow reuse

Successful tasks using `open`, `click`, `fill`, and `press` save a `WorkflowV2` in Workflows when the session finishes. Bao observes the actual DOM control during each action, saves its identity and locators, and records observed effects through the existing v1 trail contract. Snapshot refs such as `@e280` remain only in the raw capture. Field values become the existing workflow inputs. Snapshots and screenshots remain evidence, not replay actions. A settling-only check is low-confidence, not proof of the task's business result.

A second tab, popup, scroll, unsupported command options, an unaddressable target, a failed action that changed the page, or a failed or unfinished task leaves a capture only. Selecting the active tab, a failed read-only command, a harmless action failure followed by a successful action, and a completed owner handoff do not block saving. Handoffs stay out of the replay steps; replay uses its existing sign-in handling. Bao does not silently remove unsupported actions to save a partial workflow. The final tool result says `Saved workflow` with its id, or `Not saved as a workflow` with the reason. When one step blocked the save, the result names that step's id and command, such as `Not saved as a workflow: command-4 (click): its replay target could not be recorded.` A session-level reason with no step stays unprefixed. A failed `finish_task` already states the agent's reason in its first sentence. The workflow line does not repeat that reason. When nothing else blocked the save, it says the task failed. Do not claim a workflow exists without that saved result.

Saved workflows run through the current replay engine using app Replay or MCP `run_workflow`, not through native pass-through replay. Both accept the same `browser` choice, with **Running Chrome** marked as the default in the app's Run picker. A `run_workflow` call that names no browser runs on Running Chrome, except a workflow with a download or upload step, which runs on the Bao profile because Running Chrome cannot move files yet. When the remote-debugging open fails, such a call runs on the Bao profile, imports no new sign-ins, and says why. The extension route has no such fallback. An app Replay that keeps the picker's default does the same, but its fallback is the app's own `<Bao home>/chrome-profile`, not the agent profile. A LaunchServices stall does not leave either profile open; that launch stops as [Keep Bao's Chrome behind](#keep-baos-chrome-behind) describes. In the app, that choice uses Bao's own `<Bao home>/chrome-profile` with Login sites and the saved-login gate, as do Guide, capture, Sign in, import, and recheck. Agents use the separate lasting agent profile described below. The profiles use different keychains; sign-ins made in one do not appear in the other. **Fresh Chrome copy** starts a new copy for each workflow run. Replay omits only the copy's saved-tab files, keeping cookies and site storage; agent copy sessions still restore saved tabs. `run_workflow` takes an optional `profile`, the Chrome profile folder, which wins over the Settings pick. Without it, `run_workflow` and app Replay use the profile picked in Settings, or the only one. With several and none named or picked, `run_workflow` opens nothing and fails with the profiles, their names and emails, and the exact call to retry; app Replay asks the owner to pick one in Settings. On **Bao profile**, a Chrome whose profiles Bao cannot list runs with no sign-in import and says why. A `run_workflow` result that opened a browser lists in its `browser` array the same facts as the `agent_browser` `Browser:` block: the route, the Chrome app path, the user-data-dir, the Chrome profile, why Bao chose each, and each sign-in import, including the import Bao retries at a login wall on the start page. An open that fails, and a profile choice that fails before anything opens, names what Bao tried, as the `agent_browser` failure line does, and a resumed held run names the route and profile in one line. When a Bao profile or copy stops at a sign-in or check, `browser` also gives the exact `run_workflow` calls that fall back to `browser: "current"` on the same Chrome profile, unless the workflow has a file step that Running Chrome refuses. Once the run's browser opens, Bao does not switch routes on its own. When choosing the profile fails, the app's Run error names what Bao tried. A saved run that opens Running Chrome or a Chrome copy stores the route and why: the default when the Run picker stays on Running Chrome, even when the site ties its sign-in to the owner's Chrome, and picked in the Bao app when the owner picks a Chrome copy. A bound site that rewrites a Bao profile or Chrome copy pick to the owner's Chrome stores the bound reason instead, and a running-Chrome failure that then opens that copy stores fallback when running Chrome could not be used. It does not say the agent named it. **Running Chrome** opens a new task tab with focus emulation in a window of that profile, in the background when it is the profile the owner used last, so the owner's active tab and window focus stay as they were. Replay attaches only to that tab, so the owner's other tabs stay untouched, and a tab that never answers cannot stall the start. When `run_workflow` or app Replay holds for sign-in, a confirm, or a human check, Bao brings that tab to the front. The run's tab closes when the run ends, unless the run holds for the owner or Settings → Keep window open after agent finishes is on. With that setting on, the run's own tab stays and Bao only disconnects. Replay leaves the owner's browser open when it disconnects. Capture receipts, raw commands, and pictures stay in their original capture run; saving does not mark that capture as a replay or establish a green replay.

### Keep Bao's Chrome behind

Bao's own agent Chrome, on `browser: "bao"` and `browser: "copy"`, never becomes the front app and never takes the owner's keyboard while the agent works. The owner's app and its windows stay in front through launch, `open`, `tab new`, tab switches, and actions.

- **Launch.** On macOS Bao launches Chrome through LaunchServices with `-g`. If LaunchServices cannot start that Chrome, Bao stops at once and says `macOS LaunchServices cannot start Google Chrome. Restart the Mac, then try again.` A window Chrome opens for itself at launch takes the front even then, so the Bao profile starts with `--no-startup-window` and Bao opens its one window with `Target.createTarget` in the background. A copy whose profile has saved windows (`Sessions/Session_*`) restores them, and restored windows open behind. A copy with none opens Bao's window the same way as the Bao profile.
- **Agent commands.** The native agent connects to a local Bao endpoint in front of Chrome, not to Chrome's own port. Bao answers `Page.bringToFront` and `Target.activateTarget` itself and does not send them to Chrome, so a tab switch does not raise Chrome and does not change which tab the window shows. The session stays on the target the agent attached to. Each page the agent drives gets focus emulation, so clicks, typing, and screenshots work while that tab stays unselected, and `document.hasFocus()` and focus events behave as if its window had focus. `Target.createTarget`, which `tab new` sends, opens the tab in the background of the current window. Other commands pass through unchanged. Plain HTTP, such as `/json/list`, gets a 404, because Chrome's `/json` routes can raise a tab or hand out Chrome's own port. Bao's own metadata, screenshot, and workflow connections go to Chrome directly.
- **Owner handoff.** When a sign-in, a check, or `wait_for_owner` first needs the owner, Bao selects the waiting tab with `Target.activateTarget`. A later wall page in that same wait does not; [Wait for owner input in the same session](#wait-for-owner-input-in-the-same-session) owns that case. On macOS a Chrome launched with `-g` cannot make itself the front app, so Bao also sends the window to the Dock and back, which brings it back on top of every app's windows. A zoomed window comes back zoomed. A full-screen window has its own Space, so Bao leaves it there. The owner's app keeps the keyboard until the owner clicks the window. Only when the window came back on top does the wait instruction say `Bao brought this window to the front for the owner.` On macOS, if Bao's Chrome is already the front app, Bao skips the Dock raise and still selects the tab. It compares the pid from `lsappinfo` with the owned Chrome pid, because focus emulation makes `document.hasFocus()` true on every connection.

`desktop/test/unit/background-cdp.test.ts` covers the endpoint against test Chromium, including a click and a screenshot in an unselected tab while the commands that would raise Chrome are answered locally and not forwarded. It does not sample the macOS front app; the PR that added this route recorded that proof on the installed Chrome.

### Lasting Bao profile

```json
{"command":"open","args":["https://claude.ai/"],"browser":"bao"}
```

Bao stores the agent profile at `<Bao home>/agent-browser-profile`. It keeps cookies and site data after `close` and agent exit. It uses Chrome's mock keychain so a background agent can read its saved cookies without OS Keychain access. The app keeps `<Bao home>/chrome-profile` on the OS keychain. Bao does not rename, merge, or migrate either profile.

For cookie import, Bao copies the selected Chrome source's cookie database into a temporary browser profile, reads that site's cookies through CDP, and reuses the login importer's cookie and storage helpers. It does not copy or restore source tabs. The temporary Chrome runs with `--no-startup-window`, so it opens no window; on macOS it also launches without activating the app. It stays non-headless to retain OS Keychain access and closes after import. The lasting Bao browser still opens its visible window, behind the owner's apps. Every explicit open checks the selected source again, including startup. Cookies merge by name, domain, path, and partition: a source cookie replaces Bao's cookie only when its last-update time is later. Bao-only cookies stay. Bao protects live cookie changes that have not reached its disk database and keeps existing localStorage values. Empty and storage-only sources skip cookie-extraction Chrome. If that open reaches a recognized sign-in wall on another origin, Bao imports that origin and retries the requested open only when the import changed state. The same open never imports an origin twice. Bot checks, later actions, and screenshot capture never trigger that retry. It never enters credentials or answers a browser or OS prompt.

IndexedDB transfer still has no passing real-browser proof. The initial site's import uses the existing disk-copy helper; later site imports into an open browser transfer cookies and localStorage only. A cookie or storage record alone does not prove the site accepts a login.

Keep-window-open also applies to this profile. The next Bao-profile session closes that kept window before reopening the same saved profile. It also reclaims a window whose owning MCP process has exited. A second session cannot use the profile while a close is still finishing, or while another session is still open. Completed app copy runs keep their windows open but mark their leases retained, so the next copy session can reclaim them. App Bao runs use their own profile and do not hold an agent-profile lease.

### Use the owner's running Chrome

Set `browser` on the first `open` to choose the route. `"current"` (**Running Chrome**) is the default. It controls the owner's own running Google Chrome and its actual signed-in profile, not a copy. When Chrome is not running and the route uses the owner's own Chrome folder, Bao asks LaunchServices to start the signed helper, then starts Chrome in the background with `open -n -g -b com.google.Chrome` and no Chrome flags, and attaches. If that probe says LaunchServices cannot start apps, Bao does not start the owner's Chrome. An open that named running Chrome fails and says to restart the Mac. An open that named no browser tries the Bao profile, and that launch stops the same way. `-n` starts his Chrome even while a Bao-owned Chrome runs, so that window never comes to the front. When Bao cannot use running Chrome for another reason, for example without the helper's Accessibility grant, with the screen locked, or when Chrome refuses the connection, an `open` that named no browser runs in the Bao profile without a sign-in import. Its `Browser:` line says `fallback when running Chrome could not be used` and why. A later open is compared with the route that opened. The extension counts as running Chrome. A repeat of that route is allowed. A different browser says to close the session first. Omit `browser` until the session ends. If the owner's Chrome connection ends unexpectedly, Bao names the ended session and requires an explicit browser choice on the next `open`, rather than silently switching browsers.

```json
{"command":"open","args":["https://example.com/"],"browser":"current","profile":"Default"}
{"command":"snapshot","args":["-i"],"run_id":"run-..."}
{"command":"close","args":[],"run_id":"run-..."}
```

This Mac-only route uses BaoOSHelper's existing Accessibility grant. The helper opens a new inspect tab, enables Chrome's debugging checkbox if needed, and presses Chrome's native debugging Allow sheet while Bao connects. Chrome asks before every new debugging connection and keeps a sheet on screen after the program that asked has gone, so Bao makes one connection per running Chrome. The native agent-browser, workflow capture, replay, and every later session connect to a local Bao endpoint that shares it, each in its own browser session (`Target.attachToBrowserTarget`), so a Chrome launch raises the sheet once; a later task, native command, or daemon restart raises none. A sheet already present when polling starts gets a press. If the connection is still waiting and a sheet is still up at least 1 second later, Bao presses once more, at most 3 times, and does not attribute each sheet to a particular connection. It does not request Automation or Screen Recording. A locked screen, missing Accessibility access, or ambiguous browser process stops startup without asking for a new grant.

Bao opens a new task tab in a window of the chosen Chrome profile before the first navigation, and never in another profile. Chrome's debugging protocol opens tabs only in its default context, the profile the owner used last. Bao reads that context's profile folder from a hidden `chrome://version` tab. When it is the chosen profile, the task tab opens in the background, so the owner's active tab and window focus stay as they were. Otherwise Bao runs the running Chrome's own executable with `--user-data-dir` and `--profile-directory`, and Chrome opens the task tab in front, in a window of that profile. If no such tab appears, Bao says so and stops. `tab new` and `click --new-tab` are refused on a tab Chrome opened in front, because Chrome would put the new tab in its default context. It keeps focus emulation on for that tab, so the page paints, runs timers, and takes clicks and typing while the owner looks at another tab. Bao binds the native session to the task tab through agent-browser's session tab binding and starts the daemon with `--pin-tab`; a native daemon restart returns to that tab but loses refs, so take a fresh snapshot. Without the pin, the daemon makes every target it discovers current, such as a tab the owner opens or the Gemini in Chrome panel (`gemini.google.com/glic`). Chrome lists its own surfaces as debugging targets next to tabs, such as the Gemini panel and side panels. Bao counts a target as a tab only when it is a `page` target that `Browser.getWindowForTarget` places in a window's tab strip; Chrome refuses that call for a panel, a webview, or a hidden page. Tab lists leave those targets out, and `tab` refuses to switch to or close one; the lists mark Bao's task tabs `(Bao task tab)`. Before Bao reads or acts on the page, it checks the daemon's current tab. A tab that the agent's tab opened, such as a sign-in popup, becomes the agent's tab, as it does in Bao's own Chrome. On any other tab, or when the agent's tab is gone and a Bao task tab remains, Bao switches the daemon back to the agent's tab, or to its newest task tab. When the agent's tab is gone and no Bao task tab remains, because the owner closed it or the agent closed the last one, Bao ends the session and reports that Bao's task tab was closed. Start a new session with `open` and an explicit browser, the same way as when the owner's Chrome session ends. Any other command repeats that line. `close` and `finish_task` clear it. A `tab <id>` the agent runs makes that tab the agent's tab. A tab the agent opens with `tab new` or `click --new-tab` becomes the agent's tab and a task tab, as does a popup followed from a Bao task tab. On a background task tab it comes to the front, because agent-browser has no background option. When a sign-in or human check first needs the owner, Bao brings the task tab to the front. A later wall page in that same wait does not; [Wait for owner input in the same session](#wait-for-owner-input-in-the-same-session) owns that case. It keeps one browser-level CDP connection for metadata, page pictures, the tab video, and focus emulation. Stay in the current session's task tab, which shares the owner's sign-ins; use another tab only when the owner asks. The Settings Chrome profile does not pick this route's profile for `agent_browser`; the first `open` names it. It does for `run_workflow` and app replays on Running Chrome. Both routes record commands and page screenshots in Runs.

Agent sessions on Running Chrome over remote debugging also record the agent's tab to MP4 through `Page.startScreencast`, without raising Chrome or using macOS Screen Recording. The recording follows the agent's current tab. It pauses during an owner wait ([Wait for owner input in the same session](#wait-for-owner-input-in-the-same-session)). Bao ends the screencast and detaches that session before it closes its task tabs or detaches from Chrome, then encodes the MP4. The receipt's Detailed evidence section has the video and step time marks. Bao uses the existing ffmpeg lookup; when capture or encoding is unavailable, commands and page screenshots still record, and stderr says recording is unavailable. A host stop still exits within 15 seconds. SIGTERM, SIGINT, SIGHUP, and a version-check stop use that cap. If the MP4 is already written, the run keeps it, including a clip cut at the capture limit. If the encode is still running, Bao leaves that encode running after it exits and attaches the finished file to the run. If that encode fails, Bao deletes the frames and stores that the video is unavailable because Bao stopped before the video finished. It does not claim a file that is not on disk. Once the MP4 is written, Bao removes its raw frames directory, including when the encoder's supervisor exits during its last wait. The next Bao start removes a frames directory whose run already has its video. It never deletes the MP4.

`finish_task`, `close`, MCP disconnect, and handled stop signals close only task tabs Bao created, then detach from current Chrome, while that connection is still up. After the connection has already ended, from idle or a drop, and Bao did not record the task tab as closed, a later `close` does not close that tab. The step says `Disconnected from your Chrome. Bao's task tab may still be open.` Bao tracks their target ids, including tabs the agent opened with `tab new` or `click --new-tab`, and a popup the agent followed from a task tab. Pre-existing owner tabs stay open, even if the agent selected one during the task. Bao never quits, signals, or relaunches the borrowed Chrome or removes its profile. For an agent session, keep-open applies only to copied windows. A workflow run follows [Workflow reuse](#workflow-reuse). [Session end](#session-end) defines native daemon shutdown and state cleanup. Bao leaves the debugging checkbox enabled; this route does not restore the old preference or revive retired live-driver workflows.

### Session end

For every route, Bao stops only this session's native daemon before removing its private state directory. It waits up to one second after each of two SIGTERM attempts, then up to one second after SIGKILL, and verifies exit. If signaling or exit verification fails, cleanup preserves the state directory; current Chrome still detaches without closing the borrowed browser. A cleanup that fails for any reason is stored on that run as `cleanupError`, and the run keeps its outcome. A `close`, `finish_task`, or disconnect call that runs the cleanup reports it once, as `Bao could not clean up the browser session of run <run_id>: <error>`. The owner-wait timer and the agent-idle timer write that same named error to stderr only. The window-closed path stores it as `cleanupError` and does not report it. When the ended session is already gone, a newer chat's open writes that error to stderr and still starts. The open result does not include the error and does not name that run. Bao lets the session go either way, so a later call does not repeat the error. Bao lists only the Chrome processes whose command line names the session's profile, so a long process list does not break open, close, or `finish_task`; when even that list cannot be read, shutdown stops the processes Bao started and keeps a Bao-profile or copy marker for the next session to reclaim.

For the copied-profile route, `finish_task` closes the browser by default and finalizes the existing capture without adding a native close command. `close` ends only this session and removes its copy after Chrome stops. It succeeds if the owner already closed the marked window or the session already ended. Agent exit, MCP disconnect, and SIGINT/SIGTERM/SIGHUP close the marked window, delete its copy, and finish the run by default. Proxy cleanup starts at once, even when another tool call is still waiting.

In **Settings → Technical details → Agent window**, **Keep window open after agent finishes** leaves the marked window available for a manual final step. The kept window shows the tab the agent last had current. Bao selects it with `Target.activateTarget` on its direct connection before it disconnects. That selects the tab and does not bring the window to the front. This local choice is off by default and does not enable extensions. Bao still finishes the run and removes the native agent's private state. The next copied-profile agent session closes the kept window and deletes its copy before opening a fresh one, even if the setting has since been turned off. A kept copy stays on disk until the next agent session cleans it up, even if the owner closes its window by hand. Keep-open applies when `finish_task` ends a task, the agent disconnects, or Bao MCP stops. An explicit `close`, or closing the window by hand during a live session, still closes Chrome and deletes its copy. Bao never closes the source profile or another Bao home's window. With the setting on, Bao also keeps its own task tab open in the owner's running Chrome when a workflow run or an app Replay ends, and only disconnects.

Kept Chrome has no Bao owner and keeps a local debugging port open, even after you close its window, until you quit that Chrome or the next agent session reclaims its copy. Other local processes, including those run by another OS user, can use that port to read the copy's cookies or control its signed-in pages. Bao has already finished the run and no longer records those actions.

### Wait for owner input in the same session

When the active tab's URL or title signals sign-in, a verification code, Imperva, or hCaptcha, Bao returns `outcome: "halted"`. It keeps that tab, browser session, MCP process, and Library run. The page shows a **Bao is waiting for you** banner, and the Library run says **needs you**. The owner signs in or clears the check in that tab.

```json
{"command":"wait_for_owner","args":["60000"],"run_id":"run-..."}
```

The optional timeout is 1 to 120000 milliseconds, with a default of 60000. On a recognized sign-in or check it limits each check, not the whole owner wait. On any other page, and when Bao could not read the page, that deadline ends the wait. The run viewer labels the step **Wait for you to sign in or clear a check**, with the limit in seconds or minutes. Without an explicit run deadline, the wait status says **no overall timeout**. Each call stays below the 180-second MCP limit. A recognized wall is a sign-in or check URL or title, or a snapshot with a sign-in or verification dialog. On `waiting` for a recognized wall, call it again without ending the agent turn. That handoff stays open, later commands stay halted, and the Library run stays **needs you**. A page that is not a sign-in or check, and a page Bao could not read, still shows **needs you** while that call runs, and shows the banner when Bao could read the page. When the call's deadline passes without a recognized wall, Bao removes that banner and returns `recording`. The instruction says the wait is over and the run is recording. The text result has a `Run <id> · recording` line, and the card reads **The wait is over. The run is recording.** Later commands are not halted, and a later `finish_task` records the caller's outcome. Calling `wait_for_owner` again starts another wait. Temporary metadata or CDP errors keep the handoff open until the call's deadline, then end it the same way when Bao never confirmed a wall. On `recording`, take a fresh snapshot and continue in the same session. On `ready`, take a fresh snapshot and continue in the same session. On `closed`, report the returned session-ended instruction. If the owner's Chrome session ended unexpectedly, reconnect with `open` and `browser: "current"` or explicitly choose `browser: "bao"` or `browser: "copy"`; do not silently switch browsers. If Bao's task tab was closed, the result says so and the session ends; start a new session with `open` and an explicit browser. Do not start another MCP process to resume this window. If the Bao window closes during an owner wait, the owner's Chrome session ends during that wait, or the session ends while that wait is still open (the agent disconnects, `finish_task` runs, or the 30-minute limit runs out), the run finishes `failed` with reason `session_closed` and the last wait step of that open wait is recorded as failed. A wait that already finished stays as it finished. If Bao's task tab was closed instead, the run finishes `failed` with reason `Bao's task tab was closed`, and the card keeps that closed-tab sentence.

Before `wait_for_owner` starts a wait on a page whose URL and title are not a wall, it reads one snapshot to recognize an in-page sign-in or verification dialog, and does not save that snapshot. That snapshot is read before the wait starts, while the run is still recording. During the handoff poll, Bao reads only the pinned tab's URL and title through browser-level CDP. It does not run native page commands, inspect fields, read text, take further snapshots, or save screenshots. On Running Chrome over remote debugging, the tab video pauses for the handoff, including a capture that starts during it, and resumes when the wait ends. Frames from the wait are not kept. Other page commands return the handoff without recording their arguments. `close` and `finish_task` stay available to end an abandoned task; ending an unfinished handoff that way records a failed run with reason `session_closed`. A wait already ended at that deadline, because the page was not a wall, is not unfinished. `wait_for_owner` saves no page picture. Aside from that one snapshot before the wait starts, it forwards no native command.

Only `wait_for_owner` continues an owner wait. Claude Desktop keeps one Bao MCP process across chats. Pass `run_id` on `open` when continuing your own task. An `open` with no `run_id` starts a new task and ends any other open task, during a wait or not. An `open` that names a run a newer task ended does not start a new task, does not check the limit, and does not touch the open session. An `open` that names the open run keeps the task and the wait while the wait is still within the limit. It is not recorded as ended by a newer task. After the limit, that open ends the wait as `session_closed` with the `nobody continued it for 30 minutes` line and starts a new run. An `open` with a stale run id that is not a run a newer task ended still ends that wait and its session and starts a new task. When an `open` that does not name the open run finds the wait already past the limit, that ended run is failed with reason `session_closed` and the `nobody continued it for 30 minutes` line, not as ended by a newer task. When that open finds the wait still inside the limit, the ended run is recorded as failed because a newer task opened, and its task tab closes. A recognized sign-in or check wait that no `wait_for_owner` call continues ends 30 minutes after it started or the latest `wait_for_owner` call returned (`OWNER_WAIT_LIMIT_MS` in `desktop/src/cdp-live/owner-wait.ts`). Bao never ends that wait while the agent keeps continuing it, so the owner can take as long as he needs, for example to type a code a site emailed. A wait on a page that is not a wall ends at that call's deadline, so the 30-minute limit does not apply to it. A timer does this. The timer is backed up by every `agent_browser` call that names the open run, and by every `open` that does not name a run a newer task ended, because timers do not run while the Mac sleeps. `finish_task` does not back it up. A snapshot, click, `wait_for_owner`, or `close` that names another run, or names none, returns or fails before that backup and leaves the wait open. A wait the timer ends finishes `failed` with reason `session_closed`, and the window or task tab closes. The next `agent_browser` result gives one line, such as `Bao ended an earlier owner wait from 10:59 PM; a new open starts a new task.` or `...; nobody continued it for 30 minutes.` When the timer already ended the wait, `finish_task` gives that `nobody continued it for 30 minutes` line instead of leaving it for the next browser call. The sentence can still be `No browser task is open.` The call that gives the line consumes it, so a later call does not repeat it. On `finish_task` the line is its own text block, and `structuredContent.endedWait` carries the same text. [Direct MCP commands](#direct-mcp-commands) owns where that block sits.

Every `agent_browser` result that starts names the run it acted on: text clients get a `Run <run_id>` line after the sentence, and MCP Apps hosts get `run_id` in `structuredContent` and in the `run_id` and `step_id` block. A `browser` value other than `current`, `bao`, or `copy` is rejected before the call starts. The result is only `Choose browser=current (default), browser=bao, or browser=copy.` It names no run, carries no picture, pick, wait, or earlier command output, and does not read the open session. MCP calls carry no chat identity, so every command takes `run_id`, the run id from the chat's latest `agent_browser` result. That keeps one chat from acting in another's session. While a session is open, every command except a new `open` needs `run_id`. Without it the call fails with `run_id is required on <command> while a browser session is open. Send back the run id from this chat's latest agent_browser result; a chat whose results named no run has no session here.` and names no run. Any command other than `open` that names another run, or names none, changes nothing: no step, wait, banner, outcome, or closed tab, and the result does not name the open run. A command that names another run returns `closed` with `This run's browser session ended and cannot continue. Report that to the owner. Run <id> is not Bao's open browser session. The browser now belongs to another task, so stop here.` A command that names none fails with the required `run_id` error above and does not return that reply. The closed reply does not say to reconnect. A `finish_task` that names a run a newer task ended returns `no_session` with that closed reply and changes nothing, whether or not another session is open. A foreign `finish_task` for a run a newer task did not end returns `no_session` with `Run <id> is not Bao's open browser session, so finish_task changed nothing.` Pass `run_id` on `open` when continuing your own task. An `open` with no `run_id` starts a new task and ends any other open task. An `open` that names a run a newer task ended does not start a new task and does not touch the open session. An `open` with a stale run id that is not a run a newer task ended still ends the open run and starts a new task. With no session open, a command that names a run a newer task ended returns that same closed reply and changes nothing, including `open`, `snapshot`, `click`, `wait_for_owner`, `close`, and `finish_task`. An `open` with no `run_id`, or with an id that is not a run a newer task ended, still starts a new task. A `wait_for_owner` for a run whose Chrome ended gets `The owner's Chrome session ended. Reconnect with command=open and browser=current, or choose browser=bao explicitly to use Bao's lasting profile.` A run whose task tab closed gets that same reconnect sentence, starting `Bao's task tab was closed.`

The wait sentence, banner, and instruction name what the page asks, from its title first, then its address: sign in, or clear a human check. A page Bao does not recognize, or one whose title asks to confirm or verify an account or enter a code, gets neutral words: finish the check on the site. Bao never calls such a page a sign-in. The wait time reads in words, such as `waiting 4 min` or `waiting 9 h 53 min`.

During a `wait_for_owner` poll, a wall whose URL or title differs from the page this wait recorded replaces that page on the card, instruction, and banner. Bao records only the new URL and title, and uses that page as the ready-check baseline. A title change on the same URL counts. Bao replaces the banner and does not stack a second one. That replacement does not select the tab, raise the window, or bring the task tab forward, and it does not change the wait's start time or the `Bao brought this window to the front for the owner` line.

Readiness means the tab has an HTTP(S) URL and a nonblank title, its URL or title changed from the wall page this wait last recorded, neither matches a sign-in/check marker, and both stayed stable for 750 milliseconds. This is not proof of authentication. On a recognized sign-in or check, an unchanged URL and title keep waiting even if page content changes. An unrecognized check can use `wait_for_owner` to enter that private wait while the call runs; on a Bao-profile session Bao first tries Running Chrome. When the deadline passes and the page is still not a sign-in or check, that wait ends, as the timeout paragraph says. Metadata does not identify every sign-in form or embedded challenge.

## Pick an engine and profile

The **Settings → Technical details → Page engine** choice remains separate from `agent_browser`. Under **agent-browser (trial)**, saved workflows that explicitly declare `driver: "playwright"`, including supported pass-through tasks, remain searchable and replay through the same browser path as **Current engine (default)**. Other workflows still return `pass-through sessions do not support saved workflow replay`. Historical live workflows remain retired under either choice; see [retirement behavior](cdp-live.md).

Settings → Technical details → Page engine → **Chrome profile** lists existing `Default` and `Profile N` directories under either engine. Chrome's `Local State` supplies display names and account emails. Missing names fall back to the directory name; missing directories are omitted. The saved `chromeProfile` choice selects the source for MCP workflow runs and app **Fresh Chrome copy** and **Running Chrome** runs. Pass-through sessions take the folder from `profile` on the first `open`. The Settings choice is marked in the list Bao returns when Chrome has several profiles and the open names none, and it names the profile whose device-bound sites a lasting Bao profile drops. See [Choose the Chrome profile](#choose-the-chrome-profile) and [Sites that stay in running Chrome](#sites-that-stay-in-running-chrome). App **Bao profile** runs use Login sites for sign-in instead; see [Workflow reuse](#workflow-reuse).

The copied-profile route reads the selected source and creates a private copy outside the checkout. It does not launch, write to, or lock the source profile. Only the Chrome child gets the real HOME from the passwd entry so it can use the login keychain. The native command process keeps a private HOME. No remote-debugging toggle, Accessibility, Automation, or Screen Recording grant is needed. If a permission prompt appears, stop rather than approving it to keep a test running.

The copy keeps cookies, saved tabs, session-restore files, Session Storage, and encryption metadata. Cache directories are omitted. Chrome starts with sync off and `--restore-last-session`. Its light orange or blue theme differs from the source; its avatar is the origami fox, or penguin when the source already uses the fox. Extensions stay off, including copied themes. The copy has mode `0700`. Copying stops after five minutes or 20 GiB. Bao refuses links and active copies. [Session end](#session-end) defines window and copy cleanup. A released keep-open copy or a copy whose Bao process has exited can be reclaimed: Bao stops only Chrome processes using that exact marked directory before deleting it, never the source profile. The 10-minute inactivity backstop does not close a session during an active command or owner wait.

## Known gaps

Device-bound sites, left on purpose:

- Throwaway Chrome launches (heal promotion, eval, spike, proof, and launchAccountChrome) do not take the owner's device-bound list. They are not the lasting profile.
- When Settings picks a profile, a device-bound site that exists only in another profile is not purged or refused.
- The copy owner-wait hint still says Bao does not switch on its own. That is still true at a sign-in wall. Only the bound-move failure line was reworded.
- App Replay that names Bao profile falls back to the app chrome-profile, not the agent profile, when running Chrome fails on a bound site.
- With the extension as the running-Chrome route, a later open of a bound site in a Bao-profile or copy session still moves over remote debugging. There is no move into the extension relay.
- With the extension as the running-Chrome route, a named Bao-profile open of Google or the Times becomes an unread Bao profile when macOS refuses the Chrome folder, before the extension gate.
- Routing still uses the chosen Chrome profile only. A site bound only in another profile can open in the Bao profile. When that site is on the owner list, the sign-in import skips it and writes no cookies or storage. When Settings picks a profile, the gap above applies.
- Live check of refusal, purge, and running-Chrome routing is pending the alex-m1 reboot.

A wait on an in-page sign-in dialog (found by snapshot, URL and title unchanged) does not reach ready when the owner finishes the dialog in place. Fallback calls to browser=current exist only for a copy session, and for a Bao-profile session after a move to running Chrome failed. A Running Chrome session has no fallback calls, so that wait stays waiting until close or the owner-wait limit. Detecting an in-place finish needs Bao to read the page during the wait, which is a product choice.

When the agent's task tab opens two popups before Bao looks, keepTab follows only one: the last fresh tab whose opener is the tab it is already on. Only that followed popup joins the task tabs, so tab lists mark it and finish closes it. The other popup stays open in the owner's Chrome and is not marked. A popup that the followed popup later opens is tracked. A follow-up should track every popup the task tab opened, not only the one the agent followed.

A popup opened from an owner tab the agent switched to stays open and is not marked, because Bao cannot tell that popup from one the owner opened in his own tab.

A page that opens a new tab, such as a `target=_blank` link, can still bring Chrome forward: Chrome does that itself, not through the agent's commands. The installed Chrome on macOS does not, until the owner first clicks its window, for example during a handoff. A Chrome that Bao starts directly rather than through LaunchServices, which is the test browser on macOS, always can.

Running Chrome through the Bao extension is gated off. Set `"runningChromeExtension": true` in the Library's `settings.json` to use it instead of remote debugging; no screen offers it. [Running Chrome](extension.md#running-chrome) describes that route. It runs in the Chrome profile where the extension is linked and takes no `profile`.

This is Chrome's internal accessibility state, not a new macOS privacy (TCC) grant. The helper does not clear the flags on detach; full renderer accessibility stays enabled until Chrome restarts. ## Evidence

Each session creates one `kind: "capture"` run in the Library home Bao.app reads. See [Runs and Detailed evidence](v1.md#install-and-run) for the desktop controls that expose commands, screenshots, and native output. The capture receipt remains recording-only, with no replay or teaching actions; a separately saved workflow appears in Workflows. The capture omits Identity and Snapshot inspectors. Durable replay identities and observed effects live in the saved workflow's trail. Capture runs do not claim to count the outside agent's model calls or establish replay green status.

Each step stores its exact command and argv, native stdout/stderr and exit codes, error flag, start/end times, and its sentence (`summary`). Bao saves a pending `open` before startup and updates the run atomically as results arrive. Startup failure produces a failed run with its original error and no invented picture. Uncatchable process termination can leave readable partial runs marked `recording`; handled stops finish the run as described in [Session end](#session-end).

Bao takes a separate page screenshot through CDP on the active tab after each ordinary command, with a three-second deadline. On running Chrome, if that target is not a page, is not http or https, has a `/glic` path, or does not answer a short target lookup, Bao pictures its task tab instead of waiting out the capture. If a capturable active tab then fails to capture, within that capture's own three-second deadline, Bao falls back to the task tab. A copy or Bao-profile session does not fall back to another tab. When Bao keeps the task tab's picture, the tool result says the active tab could not be pictured. A task tab on a sign-in or check page is omitted. When no picture can be kept, the stored error names the cause, except `close`, which records that the session closed and no page remains. A step that ends because Bao's task tab was closed records no picture and no picture error, so the closed-tab sentence stays the cause. The [host contract](mcp-viewer.md#host-contract) names when the tool result includes that cause. Owner handoffs and every `wait_for_owner` call omit page pictures and native screenshot copies. The Running Chrome tab video also pauses for that wait. This does not change native refs or screenshot history. Native screenshot files, including relative and default paths, are copied into `shots/runs/<runId>/` before the private state directory disappears. After `close`, the step records the missing page rather than reusing a picture. A recording or screenshot failure logs a warning. Neither changes native command forwarding.

A finished tab video from a Running Chrome agent session over remote debugging is `videos/<runId>.mp4`. See [Use the owner's running Chrome](#use-the-owners-running-chrome) for capture, the owner-wait pause, and a host stop that still attaches a finished file.

**Raw command arguments, results, screenshots, and that tab video can contain credentials. This route does not redact them. Do not send data you do not want saved locally.** Saved-workflow input persistence is a separate contract in [permissions](permissions.md#secret-text-in-saved-files).
