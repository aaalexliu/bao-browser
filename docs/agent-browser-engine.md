# agent-browser pass-through

## Direct MCP commands

`bao mcp` exposes `agent_browser` and `finish_task`. Call `finish_task` before the final chat reply for every completed, failed, or cancelled browser task. A long-lived MCP connection has no conversation-turn-end event, so a final answer alone cannot release the browser.

```json
{"name":"finish_task","arguments":{"outcome":"passed","reason":"Verified the requested change on the page.","task":"Add milk"}}
{"name":"finish_task","arguments":{"outcome":"failed","reason":"The requested item was unavailable."}}
{"name":"finish_task","arguments":{"outcome":"passed","reason":"Cancelled both subscriptions.","done":["Cancelled Coix Seed","Cancelled Barley Tea"]}}
```

`task` is optional. It is a short name for the run, such as the request you carried out. Omit it when you have no task name. Bao stores a trimmed non-blank value and drops a blank one. [Runs](v1.md#install-and-run) uses that stored name in the list. `done` is optional too: at most 50 short items, one per thing the task did. The finished card lists them; without them it shows the reason and step counts. The result's text is one sentence of the outcome, the run line, then the workflow save result; the receipt is in `structuredContent`.

Use `finish_task`, not `close`, to end a task. It returns a sentence of the result, a `Run <run_id> · <status> · <link>` line, and the workflow save result in words, with the full run receipt in `structuredContent`, without stopping MCP, so the same client can start the next task. If session cleanup is still running, `finish_task` waits and applies the outcome to that same session's run only if it has no outcome yet. Once the session is fully removed, `finish_task` returns `no_session` and leaves earlier runs and saved workflows unchanged. Call `finish_task` before `close`; a late finish cannot change the status that a completed close computed. The agent's checked outcome and reason set the capture result, even after a recovered command failure. Earlier command failures stay in the receipt; workflow saving keeps its existing harmless-failure rule. An incomplete owner wait still fails with `session_closed`. Explicit task outcomes include a reason; a session ended without an outcome keeps its step-derived status without adding an outcome envelope. Do not finish while waiting for sign-in, `wait_for_owner`, or an owner confirmation. After 10 minutes without an agent command, Bao ends a non-waiting session as failed with a plain reason that the agent never finished the task. Active commands, owner waits, sign-in handoffs, and held replay confirmations do not expire. Idle cleanup honors keep-open for owned windows and only detaches from current Chrome, leaving its task tabs open. Settings Stop remains the replay heal policy; task completion neither heals nor calls a model.

`agent_browser` needs no running Bao app unless the gated [extension route](extension.md#running-chrome) is on. It accepts a native `command` and an `args` array. Each item is one CLI argument, without shell quoting. Supported commands are `open`, `snapshot`, `click`, `fill`, `press`, `scroll`, `tab`, `screenshot`, `wait_for_owner`, and `close`.

```json
{"command":"open","args":["http://127.0.0.1:8080/"]}
{"command":"snapshot","args":["-i"]}
{"command":"tab","args":["t2"]}
{"command":"fill","args":["@e1","hello"]}
{"command":"click","args":["@e2"]}
{"command":"close","args":[]}
```

A plain `snapshot` returns the whole native tree, often 5,000 to 20,000 characters on a real site. Two snapshot options keep the result short. Bao still runs the full native snapshot and records it in the run; only the text the agent gets changes.

- `find` takes `text`, `role`, or both. It returns only the lines whose accessible name or value contains `text` (any case) and whose role is `role`, each with its ref, the lines that hold it, and everything inside it, in page order. Refs and attributes are not searched. A miss says so in one line.
- `diff: true` returns only the lines added (`+`) or removed (`-`) since the session's last snapshot with the same `args`, with the unchanged lines that hold them. With no earlier snapshot for those `args`, or when the diff would not be shorter than the page, it returns the full tree with one line saying why. An unchanged page returns one line.

```json
{"command":"snapshot","args":[],"find":{"text":"Sign in","role":"button"}}
{"command":"snapshot","args":["-i"],"diff":true}
```

Both are accepted only on `snapshot`, one at a time. `click`, `fill`, and `press` results stay one sentence plus native status, then the picture line the [host contract](mcp-viewer.md#host-contract) names when it applies. The sentence names the new page when the address changed.

Bao fixes one session in a private socket directory, installed Google Chrome, and a visible window. On the Bao profile and copy routes that window stays behind the owner's apps; see [Keep Bao's Chrome behind](#keep-baos-chrome-behind). On `open`, `browser: "current"` (the default, **Running Chrome**) uses the owner's own running Chrome on one of his Chrome profiles, with the sign-ins he already has, as described below. `browser: "bao"` (**Bao profile**) uses Bao's separate lasting agent profile, imports site sign-ins from that Chrome profile, and keeps sign-ins and site data between runs. `browser: "copy"` (**Fresh Chrome copy**) starts a fresh marked copy of that Chrome profile. Bao uses the Bao profile or a copy only when the agent names it. Close the session before changing browser or profile.

#### Sites that stay in running Chrome

Some sites tie their sign-in to the owner's own Chrome. Google binds its session to a key on his Mac (device-bound sessions), so a copied Google sign-in used in another browser signs him out everywhere. The Times counts each browser that holds its session as one more device and asks for a code. So Bao opens these sites only in the owner's running Chrome:

- Google: `google.com` and its subdomains, Google's country sites such as `google.co.uk`, and `youtube.com`.
- `nytimes.com` and its subdomains.
- Any site listed in the Chrome profile's `Device Bound Sessions` table. Bao reads only the table's `key` column, one site per row.

A first `open` of such a site goes straight to running Chrome on the same Chrome profile, even when it names `browser: "bao"` or `browser: "copy"`. Two cases stay out: a workflow with a download or upload step runs on the browser it names, and when Bao cannot use running Chrome the site opens in the Bao profile with no sign-in import, or stays in the copy without its sign-in. Its `Browser:` line gives the reason `this site ties its sign-in to your Chrome`. A LaunchServices stall stops that launch instead, as [Keep Bao's Chrome behind](#keep-baos-chrome-behind) describes. A later `open` of such a site in a Bao-profile or copy session moves the session to running Chrome before any import, with the line `Bao did not open www.nytimes.com in its own browser because this site ties its sign-in to your Chrome; continued in your running Chrome (Chrome profile "Default", Alex) over remote debugging. Take a fresh snapshot before acting.` A sign-in wall on such a site, such as Google's account page, imports nothing and moves the same way.

Bao never writes a Google sign-in cookie (`SID`, `HSID`, `SSID`, `APISID`, `SAPISID`, `SIDCC`, `LSID`, `OSID`, `LOGIN_INFO`, and the `__Secure-` and `__Host-` forms of them) into a profile it owns, whatever the site, including the app's Login sites profile. It also never writes a Times cookie, nor a cookie of a site in the `Device Bound Sessions` table of the Chrome profile it imports from. Every Bao-owned profile, the agent's Bao profile and the app's `<Bao home>/chrome-profile` alike, loses its Google sign-in and Times cookies while its Chrome is stopped, each time Bao starts that Chrome. Device-bound sites count only where Bao has the owner's Chrome profile to read: a Bao-profile open that imports from a Chrome profile also drops that profile's device-bound sites' cookies, and the app sends a run to running Chrome for a device-bound site only when a Chrome profile is picked in Settings. A Chrome copy leaves all of these cookies and the `Device Bound Sessions` table out. A copy is also not signed in to Chrome: Bao deletes the rows of the `token_service` table in its `Web Data`, which hold the Google account's refresh token, keeps the rest of `Web Data`, such as autofill, and clears the signed-in account from its `Preferences`. The app's Login sites refuse these sites with a plain line and do not probe them; they use the owner's running Chrome instead. `bao import-login` refuses Google, YouTube, and the Times, and writes no device-bound site's cookie from the Chrome profile it reads. An app run whose start page is such a site runs in running Chrome, even with **Bao profile** picked, unless the workflow has a file step. A sign-in import reads the owner's cookies in a helper Chrome that holds only the target site's cookies and cannot reach any host (`--disable-background-networking`, `--no-proxy-server`, and `--host-resolver-rules="MAP * ~NOTFOUND"`).

### Choose the Chrome profile

The first `open` names the Chrome profile folder with `profile`, such as `"Default"` or `"Profile 2"`. Bao lists the `Default` and `Profile N` folders in Chrome's user-data-dir, with display names and account emails from Chrome's `Local State`. When Chrome has one profile, Bao uses it and says so. When Chrome has more than one and the call names none, Bao opens nothing and records no run. The result's sentence lists every profile with its folder, name, and email, marks the one picked in Bao Settings, and the next text block gives the exact call to retry. `structuredContent` has status `needs_profile`, not an owner wait, with the sentence as `summary`, the call as `retry`, and the same profiles. A folder Chrome does not have is an error that lists the valid ones. Bao never falls back to `Default` on its own.

```json
{"command":"open","args":["https://www.nytimes.com/"],"browser":"bao","profile":"Default"}
```

Every `open` result has a `Browser:` text block after the native output. It names the route (Bao profile, Chrome copy, Running Chrome over remote debugging, or the gated extension), the Chrome app path, the user-data-dir, and the Chrome profile folder with its name and email, and says why each was chosen: the default, named by the agent, the only profile, the fallback after a sign-in wall, `this site ties its sign-in to your Chrome`, or the fallback when running Chrome could not be used. The Library run stores the same facts in its `browser` field. On a Bao-profile session, each sign-in import adds a `Sign-in import` block: the site, the Chrome profile, how many of the site's cookies Bao read, and how many cookies and storage items it wrote into its profile, or why it could not read the Chrome profile. The run keeps each import in `signInImports`. Every later result in the session, including `finish_task`, ends with one short line that names the route and Chrome profile, such as `Browser: Bao profile, Chrome profile "Default".` An open that fails names what Bao tried, after the error: the route, why, the Chrome app path, and the profile folder.

On macOS 27 and later, reading Chrome's folder needs System Settings > Privacy & Security > Files & Folders > (app) > Google Chrome; [What Bao asks permission for](permissions.md#files--folders--google-chrome) says which app. Without it, every read Bao makes there fails with one message that names the switch and the app, such as `macOS did not let Bao read Google Chrome's folder (EPERM on ~/Library/Application Support/Google/Chrome). Turn on System Settings > Privacy & Security > Files & Folders > Bao > Google Chrome, then try again.` The Bao profile still opens: its `Browser:` line says `Bao imports no sign-ins:` with that message, and a refused cookie file shows the same message in the `Sign-in import` block. A Chrome copy and a named Running Chrome stop with it. An `open` or run that named no browser opens the Bao profile instead, with the reason `fallback when running Chrome could not be used`. Running Chrome checks the folder before the helper touches Chrome, and a refused `DevToolsActivePort` is reported as refused, not as `Chrome did not open its debugging port`.

```text
Browser: Bao profile, named by the agent. Chrome app: /Applications/Google Chrome.app/Contents/MacOS/Google Chrome. User data: <Bao home>/agent-browser-profile. Sign-ins come from Chrome profile "Default" (Alex, alex@example.com) in ~/Library/Application Support/Google/Chrome, named by the agent.
```

When a Bao-profile session stops at a sign-in or human check, Bao moves it to the owner's running Chrome over remote debugging by itself, on the Chrome profile its sign-in import read. The owner's running Chrome holds his own sign-in and is a device the site already knows. Bao moves when an open or later command lands on a sign-in or check URL or title, when a snapshot shows a sign-in wall drawn in the page, and when the agent calls `wait_for_owner`. A wall in the page is a dialog with sign-in or verification wording and a password field, a code field, or a send-a-code control inside it, or a main heading with that wording and such a control on the page; `desktop/src/cdp-live/page-wall.ts` holds the rule. Bao opens the same page in a task tab of that profile, keeps the same session and Library run, and closes its own window. A snapshot that found the wall returns a new snapshot of the task tab. A click, fill, press, scroll, tab, or screenshot that met the wall before it ran does not run: Bao records that step as the open it ran in the task tab and returns the open output, and the agent takes a fresh snapshot before it acts. The result's first sentence says so, such as `Bao's own browser hit a sign-in or verification prompt on www.nytimes.com; continued in your running Chrome (Chrome profile "Default", Alex) over remote debugging. Take a fresh snapshot before acting.`, and the run keeps that sentence on the step, so it shows that earlier steps ran in Bao's own browser. The full `Browser:` line of the new route follows. When Chrome is not running, remote debugging is refused, or the profile window does not open, the line says why and the owner wait stays in Bao's window. Bao does not try again on its own, but every later `wait_for_owner` tries Running Chrome again before it waits, and waits for the time its timeout has left, but at least 5 seconds, or the whole timeout when that is shorter, so a slow failed move still leaves time to see the owner clear the wall. While the session stays in Bao's window after a failed move, halted and waiting results give the exact calls to fall back: close this session, then open the same site with `browser: "current"` on the same Chrome profile. A wait in Running Chrome is a real wait. When a copy session stops for a sign-in or check, the wait instruction names the fallback instead: close this session, then open the same site with `browser: "current"` on the same Chrome profile; a copy does not switch on its own. When the last session ended while a Bao profile or copy waited for the owner, the next `browser: "current"` open's `Browser:` line says it is the fallback after a sign-in wall. The page-engine choice does not affect this tool. For copied and Bao-owned profiles, extensions stay disabled and Bao launches Chrome itself. The current route leaves the running browser's extensions unchanged. Bao attaches the pinned native agent-browser through `--cdp`.

For copied and Bao-owned profiles, Bao picks a nonzero debugging port. Port zero makes headed Chrome set `navigator.webdriver` to true. Bao accepts only the WebSocket endpoint its own Chrome child prints to stderr, then writes that endpoint to the owned profile's `DevToolsActivePort` file. A port-bind race starts a direct Chrome again on a new port rather than attaching to another browser. The macOS open launcher is not started again. The current route reads the running Chrome's `DevToolsActivePort` and accepts it only when the listener PID matches the selected Chrome process.

Pass-through startup connects only to Chrome's browser-level CDP endpoint and discovers targets without attaching Playwright to restored tabs. An unrelated unresponsive renderer does not block startup. Bao leaves those tabs in place without waiting for page readiness or parking startup pages. On `browser: "copy"`, Bao opens a new blank background tab beside the restored tabs and binds the native session to it, so the first `open` loads there. The restored tabs stay untouched, and Bao knows the bound target. Like any tab the agent opens on this route, it opens in the background, so the copy never lifts Chrome over the owner's apps; focus emulation keeps it visible and its timers running. Bao waits up to 15 seconds for Chrome to show its first restored page before it opens that tab, so the tab joins the restored window instead of a window of its own. When Chrome shows only startup pages, such as a New Tab page, Bao binds the native session to that tab and opens no second one. Without that tab the native daemon drove the first restored tab that answered and navigated it away. Before focus emulation that tab was often hidden, and a logged-out x.com reached its load event after 3.1 to 24.4 seconds there, against the native 25-second load deadline; in a visible tab it took 0.36 to 0.43 seconds. The session's first native call starts the native daemon, which attaches to every tab and takes about 6 seconds with 20 restored tabs. Only the session's end bounds that call; the workflow recorder's usual 5-second tab read used to cut it off, and the capture could not be saved as a workflow. Successful `open` adds native `tab list` output. For `browser: "copy"`, the agent can switch to a signed-in restored tab with `tab <id>`; Bao does not guess its login state. `tab list --json` exposes CDP target ids.

`desktop/test/unit/agent-browser-startup.test.ts` covers startup with a stalled restored renderer, and a copy with 20 restored tabs that opens a timer-heavy page in its own tab, keeps every restored tab, and saves the task as a workflow. `desktop/test/unit/chrome-startup.test.ts` covers launch flags, a stale endpoint file, a port-bind race, browser-only startup commands, and headed `navigator.webdriver` before and after a Runtime-domain attach.

Every call's first text block is one sentence of what the step did, such as `Went to https://example.com/ ("Example")` or `Clicked "Save" (button)`. The quoted name comes from the latest snapshot line for the ref. Native stdout and stderr follow as separate MCP text blocks; a snapshot with `find` or `diff` gives Bao's shorter view of its stdout instead. A picture text block can follow that output. The [host contract](mcp-viewer.md#host-contract) names when it is left out. Sign-in and human-check handoffs follow the sentence with Bao's wait status instead. Without MCP Apps, that status is a `Run <run_id> · <outcome>` line and the instruction in words, and `structuredContent` carries the `outcome` and `instruction`. [Browser tool cards](mcp-viewer.md#browser-tool-cards) describes the visual result and receipt handoff in MCP Apps hosts. A native failure sets `isError` and leaves the session available unless the command is `close`, which attempts cleanup even after a native failure. Bao does not block final clicks. Closing a successful, representable single-document task saves a replayable workflow. The closing result gives its workflow id or one line explaining why it was not saved. A saved file that is not [schema v4](workflow-schema.md) is not loaded.

### Workflow reuse

Successful tasks using `open`, `click`, `fill`, and `press` save a `WorkflowV2` in Workflows when the session finishes. Bao observes the actual DOM control during each action, saves its identity and locators, and records observed effects through the existing v1 trail contract. Snapshot refs such as `@e280` remain only in the raw capture. Field values become the existing workflow inputs. Snapshots and screenshots remain evidence, not replay actions. A settling-only check is low-confidence, not proof of the task's business result.

A second tab, popup, scroll, unsupported command options, an unaddressable target, a failed action that changed the page, or a failed or unfinished task leaves a capture only. Selecting the active tab, a failed read-only command, a harmless action failure followed by a successful action, and a completed owner handoff do not block saving. Handoffs stay out of the replay steps; replay uses its existing sign-in handling. Bao does not silently remove unsupported actions to save a partial workflow. The final tool result says `Saved workflow` with its id, or `Not saved as a workflow` with the reason. When one step blocked the save, the result names that step's id and command, such as `Not saved as a workflow: command-4 (click): its replay target could not be recorded.` A session-level reason with no step stays unprefixed. Do not claim a workflow exists without that saved result.

Saved workflows run through the current replay engine using app Replay or MCP `run_workflow`, not through native pass-through replay. Both accept the same `browser` choice, with **Running Chrome** marked as the default in the app's Run picker. A `run_workflow` call that names no browser runs on Running Chrome, except a workflow with a download or upload step, which runs on the Bao profile because Running Chrome cannot move files yet. When Bao cannot use running Chrome, such a call runs on the Bao profile, imports no new sign-ins, and says why. An app Replay that keeps the picker's default does the same, but its fallback is the app's own `<Bao home>/chrome-profile`, not the agent profile. A LaunchServices stall does not leave either profile open; that launch stops as [Keep Bao's Chrome behind](#keep-baos-chrome-behind) describes. In the app, that choice uses Bao's own `<Bao home>/chrome-profile` with Login sites and the saved-login gate, as do Guide, capture, Sign in, import, and recheck. Agents use the separate lasting agent profile described below. The profiles use different keychains; sign-ins made in one do not appear in the other. **Fresh Chrome copy** starts a new copy for each workflow run. Replay omits only the copy's saved-tab files, keeping cookies and site storage; agent copy sessions still restore saved tabs. `run_workflow` takes an optional `profile`, the Chrome profile folder, which wins over the Settings pick. Without it, `run_workflow` and app Replay use the profile picked in Settings, or the only one. With several and none named or picked, `run_workflow` opens nothing and fails with the profiles, their names and emails, and the exact call to retry; app Replay asks the owner to pick one in Settings. On **Bao profile**, a Chrome whose profiles Bao cannot list runs with no sign-in import and says why. A `run_workflow` result that opened a browser lists in its `browser` array the same facts as the `agent_browser` `Browser:` block: the route, the Chrome app path, the user-data-dir, the Chrome profile, why Bao chose each, and each sign-in import, including the import Bao retries at a login wall on the start page. An open that fails names what Bao tried, and a resumed held run names the route and profile in one line. When a Bao profile or copy stops at a sign-in or check, `browser` also gives the exact `run_workflow` calls that fall back to `browser: "current"` on the same Chrome profile, unless the workflow has a file step that Running Chrome refuses. Once the run's browser opens, Bao does not switch routes on its own. App Replay shows none of these lines. **Running Chrome** opens a new task tab with focus emulation in a window of that profile, in the background when it is the profile the owner used last, so the owner's active tab and window focus stay as they were. Replay attaches only to that tab, so the owner's other tabs stay untouched, and a tab that never answers cannot stall the start. When `run_workflow` or app Replay holds for sign-in, a confirm, or a human check, Bao brings that tab to the front. The run's tab closes when the run ends, unless the run holds for the owner or Settings → Keep window open after agent finishes is on. With that setting on, the run's own tab stays and Bao only disconnects. Replay leaves the owner's browser open when it disconnects. Capture receipts, raw commands, and pictures stay in their original capture run; saving does not mark that capture as a replay or establish a green replay.

### Keep Bao's Chrome behind

Bao's own agent Chrome, on `browser: "bao"` and `browser: "copy"`, never becomes the front app and never takes the owner's keyboard while the agent works. The owner's app and its windows stay in front through launch, `open`, `tab new`, tab switches, and actions.

- **Launch.** On macOS Bao launches Chrome through LaunchServices with `-g`. If LaunchServices cannot start that Chrome, Bao stops at once and says `macOS LaunchServices cannot start Google Chrome. Restart the Mac, then try again.` A window Chrome opens for itself at launch takes the front even then, so the Bao profile starts with `--no-startup-window` and Bao opens its one window with `Target.createTarget` in the background. A copy whose profile has saved windows (`Sessions/Session_*`) restores them, and restored windows open behind. A copy with none opens Bao's window the same way as the Bao profile.
- **Agent commands.** The native agent connects to a local Bao endpoint in front of Chrome, not to Chrome's own port. Bao answers `Page.bringToFront` and `Target.activateTarget` itself, so a tab switch changes the agent's tab without raising Chrome. `Target.createTarget`, which `tab new` sends, opens the tab in the background of the current window. Each page the agent drives gets focus emulation, so it stays visible and keeps painting, and `document.hasFocus()` and focus events behave as if its window had focus. Other commands pass through unchanged. Plain HTTP, such as `/json/list`, gets a 404, because Chrome's `/json` routes can raise a tab or hand out Chrome's own port. Bao's own metadata, screenshot, and workflow connections go to Chrome directly.
- **Owner handoff.** When a sign-in, a check, or `wait_for_owner` needs the owner, Bao selects the waiting tab with `Target.activateTarget`. On macOS a Chrome launched with `-g` cannot make itself the front app, so Bao also sends the window to the Dock and back, which brings it back on top of every app's windows. A zoomed window comes back zoomed. A full-screen window has its own Space, so Bao leaves it there. The owner's app keeps the keyboard until the owner clicks the window. Only when the window came back on top does the wait instruction say `Bao brought this window to the front for the owner.`

`desktop/test/unit/background-cdp.test.ts` covers the endpoint against test Chromium. It does not sample the macOS front app; the PR that added this route recorded that proof on the installed Chrome.

### Lasting Bao profile

```json
{"command":"open","args":["https://claude.ai/"],"browser":"bao"}
```

Bao stores the agent profile at `<Bao home>/agent-browser-profile`. It keeps cookies and site data after `close` and agent exit. It uses Chrome's mock keychain so a background agent can read its saved cookies without OS Keychain access. The app keeps `<Bao home>/chrome-profile` on the OS keychain. Bao does not rename, merge, or migrate either profile.

For cookie import, Bao copies the selected Chrome source's cookie database into a temporary browser profile, reads that site's cookies through CDP, and reuses the login importer's cookie and storage helpers. It does not copy or restore source tabs. The temporary Chrome runs with `--no-startup-window`, so it opens no window; on macOS it also launches without activating the app. It stays non-headless to retain OS Keychain access and closes after import. The lasting Bao browser still opens its visible window, behind the owner's apps. Every explicit open checks the selected source again, including startup. Cookies merge by name, domain, path, and partition: a source cookie replaces Bao's cookie only when its last-update time is later. Bao-only cookies stay. Bao protects live cookie changes that have not reached its disk database and keeps existing localStorage values. Empty and storage-only sources skip cookie-extraction Chrome. If that open reaches a recognized sign-in wall on another origin, Bao imports that origin and retries the requested open only when the import changed state. The same open never imports an origin twice. Bot checks, later actions, and screenshot capture never trigger that retry. It never enters credentials or answers a browser or OS prompt.

IndexedDB transfer still has no passing real-browser proof. The initial site's import uses the existing disk-copy helper; later site imports into an open browser transfer cookies and localStorage only. A cookie or storage record alone does not prove the site accepts a login.

Keep-window-open also applies to this profile. The next Bao-profile session closes that kept window before reopening the same saved profile. It also reclaims a window whose owning MCP process has exited or whose explicit close is still finishing. Another active session must close before a second session can use it. Completed app copy runs keep their windows open but mark their leases retained, so the next copy session can reclaim them. App Bao runs use their own profile and do not hold an agent-profile lease.

### Use the owner's running Chrome

Set `browser` on the first `open` to choose the route. `"current"` (**Running Chrome**) is the default. It controls the owner's own running Google Chrome and its actual signed-in profile, not a copy. When Chrome is not running and the route uses the owner's own Chrome folder, Bao asks LaunchServices to start the signed helper, then starts Chrome in the background with `open -n -g -b com.google.Chrome` and no Chrome flags, and attaches. If that probe says LaunchServices cannot start apps, Bao does not start the owner's Chrome. An open that named running Chrome fails and says to restart the Mac. An open that named no browser tries the Bao profile, and that launch stops the same way. `-n` starts his Chrome even while a Bao-owned Chrome runs, so that window never comes to the front. When Bao cannot use running Chrome for another reason, for example without the helper's Accessibility grant, with the screen locked, or when Chrome refuses the connection, an `open` that named no browser runs in the Bao profile without a sign-in import. Its `Browser:` line says `fallback when running Chrome could not be used` and why. Later calls inherit that choice; omit `browser` until the session ends. If the owner's Chrome connection ends unexpectedly, Bao names the ended session and requires an explicit browser choice on the next `open`, rather than silently switching browsers.

```json
{"command":"open","args":["https://example.com/"],"browser":"current","profile":"Default"}
{"command":"snapshot","args":["-i"]}
{"command":"close","args":[]}
```

This Mac-only route uses BaoOSHelper's existing Accessibility grant. The helper opens a new inspect tab, enables Chrome's debugging checkbox if needed, and presses Chrome's native debugging Allow sheet while Bao connects. Chrome asks before every new debugging connection and keeps a sheet on screen after the program that asked has gone, so Bao makes one connection per session. The native agent-browser, workflow capture, and replay connect to a local Bao endpoint that shares it, each in its own browser session (`Target.attachToBrowserTarget`), so a session raises the sheet once; native commands and daemon restarts raise none. Sheets already present when polling starts may also be approved; Bao does not attribute each sheet to a particular connection. It does not request Automation or Screen Recording. A locked screen, missing Accessibility access, or ambiguous browser process stops startup without asking for a new grant.

Bao opens a new task tab in a window of the chosen Chrome profile before the first navigation, and never in another profile. Chrome's debugging protocol opens tabs only in its default context, the profile the owner used last. Bao reads that context's profile folder from a hidden `chrome://version` tab. When it is the chosen profile, the task tab opens in the background, so the owner's active tab and window focus stay as they were. Otherwise Bao runs the running Chrome's own executable with `--user-data-dir` and `--profile-directory`, and Chrome opens the task tab in front, in a window of that profile. If no such tab appears, Bao says so and stops. `tab new` and `click --new-tab` are refused on a tab Chrome opened in front, because Chrome would put the new tab in its default context. It keeps focus emulation on for that tab, so the page paints, runs timers, and takes clicks and typing while the owner looks at another tab. Bao binds the native session to the task tab through agent-browser's session tab binding and starts the daemon with `--pin-tab`; a native daemon restart returns to that tab but loses refs, so take a fresh snapshot. Without the pin, the daemon makes every target it discovers current, such as a tab the owner opens or the Gemini in Chrome panel (`gemini.google.com/glic`). Chrome lists its own surfaces as debugging targets next to tabs, such as the Gemini panel and side panels. Bao counts a target as a tab only when it is a `page` target that `Browser.getWindowForTarget` places in a window's tab strip; Chrome refuses that call for a panel, a webview, or a hidden page. Tab lists leave those targets out, and `tab` refuses to switch to or close one; the lists mark Bao's task tabs `(Bao task tab)`. Before Bao reads or acts on the page, it checks the daemon's current tab. A tab that the agent's tab opened, such as a sign-in popup, becomes the agent's tab, as it does in Bao's own Chrome. On any other tab, or when the agent's tab is gone and a Bao task tab remains, Bao switches the daemon back to the agent's tab, or to its newest task tab. When the agent's tab is gone and no Bao task tab remains, because the owner closed it or the agent closed the last one, Bao ends the session and reports that Bao's task tab was closed. Start a new session with `open` and an explicit browser, the same way as when the owner's Chrome session ends. Any other command repeats that line. `close` and `finish_task` clear it. A `tab <id>` the agent runs makes that tab the agent's tab. A tab the agent opens with `tab new` or `click --new-tab` becomes the agent's tab and a task tab, as does a popup followed from a Bao task tab. On a background task tab it comes to the front, because agent-browser has no background option. When a sign-in or human check needs the owner, Bao brings the task tab to the front. It keeps one browser-level CDP connection for metadata, page pictures, and focus emulation. Stay in the current session's task tab, which shares the owner's sign-ins; use another tab only when the owner asks. The Settings Chrome profile does not pick this route's profile for `agent_browser`; the first `open` names it. It does for `run_workflow` and app replays on Running Chrome. Both routes record commands and page screenshots in Runs.

`finish_task`, `close`, MCP disconnect, and handled stop signals close only task tabs Bao created, then detach from current Chrome. Bao tracks their target ids, including tabs the agent opened with `tab new` or `click --new-tab`, and a popup the agent followed from a task tab. Pre-existing owner tabs stay open, even if the agent selected one during the task. Bao never quits, signals, or relaunches the borrowed Chrome or removes its profile. For an agent session, keep-open applies only to copied windows. A workflow run follows [Workflow reuse](#workflow-reuse). [Session end](#session-end) defines native daemon shutdown and state cleanup. Bao leaves the debugging checkbox enabled; this route does not restore the old preference or revive retired live-driver workflows.

### Session end

For every route, Bao stops only this session's native daemon before removing its private state directory. It waits up to one second after each of two SIGTERM attempts, then up to one second after SIGKILL, and verifies exit. If signaling or exit verification fails, cleanup preserves the state directory; current Chrome still detaches without closing the borrowed browser. A cleanup that fails for any reason is reported once, by the call that ran it, as `Bao could not clean up the browser session of run <run_id>: <error>`. The run keeps its outcome and stores the error as `cleanupError`. Bao then lets the session go, so the next call starts fresh instead of repeating the error. Bao lists only the Chrome processes whose command line names the session's profile, so a long process list does not break open, close, or `finish_task`; when even that list cannot be read, shutdown stops the processes Bao started and keeps a Bao-profile or copy marker for the next session to reclaim.

For the copied-profile route, `finish_task` closes the browser by default and finalizes the existing capture without adding a native close command. `close` ends only this session and removes its copy after Chrome stops. It succeeds if the owner already closed the marked window or the session already ended. Agent exit, MCP disconnect, and SIGINT/SIGTERM/SIGHUP close the marked window, delete its copy, and finish the run by default. Proxy cleanup starts at once, even when another tool call is still waiting.

In **Settings → Technical details → Agent window**, **Keep window open after agent finishes** leaves the marked window available for a manual final step. This local choice is off by default and does not enable extensions. Bao still finishes the run and removes the native agent's private state. The next copied-profile agent session closes the kept window and deletes its copy before opening a fresh one, even if the setting has since been turned off. A kept copy stays on disk until the next agent session cleans it up, even if the owner closes its window by hand. Keep-open applies when `finish_task` ends a task, the agent disconnects, or Bao MCP stops. An explicit `close`, or closing the window by hand during a live session, still closes Chrome and deletes its copy. Bao never closes the source profile or another Bao home's window. With the setting on, Bao also keeps its own task tab open in the owner's running Chrome when a workflow run or an app Replay ends, and only disconnects.

Kept Chrome has no Bao owner and keeps a local debugging port open, even after you close its window, until you quit that Chrome or the next agent session reclaims its copy. Other local processes, including those run by another OS user, can use that port to read the copy's cookies or control its signed-in pages. Bao has already finished the run and no longer records those actions.

### Wait for owner input in the same session

When the active tab's URL or title signals sign-in, a verification code, Imperva, or hCaptcha, Bao returns `outcome: "halted"`. It keeps that tab, browser session, MCP process, and Library run. The page shows a **Bao is waiting for you** banner, and the Library run says **needs you**. The owner signs in or clears the check in that tab.

```json
{"command":"wait_for_owner","args":["60000"]}
```

The optional timeout is 1 to 120000 milliseconds, with a default of 60000. It limits each check, not the whole owner wait. The run viewer labels the step **Wait for you to sign in or clear a check**, with the limit in seconds or minutes. Without an explicit run deadline, the wait status says **no overall timeout**. Each call stays below the 180-second MCP limit. On `waiting`, call it again without ending the agent turn. Temporary metadata or CDP errors keep the handoff open until the call's deadline. On `ready`, take a fresh snapshot and continue in the same session. On `closed`, report the returned session-ended instruction. If the owner's Chrome session ended unexpectedly, reconnect with `open` and `browser: "current"` or explicitly choose `browser: "bao"` or `browser: "copy"`; do not silently switch browsers. If Bao's task tab was closed, the result says so and the session ends; start a new session with `open` and an explicit browser. Do not start another MCP process to resume this window. If the owner's Chrome session ends during an owner wait, the run finishes `failed` with reason `session_closed` and the running wait step is recorded as failed. If Bao's task tab was closed instead, the run finishes `failed` with reason `Bao's task tab was closed`, and the card keeps that closed-tab sentence.

During handoff, Bao polls only the pinned tab's URL and title through browser-level CDP. It does not run native page commands, inspect fields, read text, take snapshots, or save screenshots. Other page commands return the handoff without recording their arguments. `close` and `finish_task` stay available to end an abandoned task; ending an unfinished handoff that way records a failed run with reason `session_closed`. `wait_for_owner` never forwards a native command or saves a page picture.

Only `wait_for_owner` continues an owner wait. Claude Desktop keeps one Bao MCP process across chats, so a new chat's `open` would otherwise land on an older chat's wait. An `open` during an owner wait ends that wait and its session, then starts a new task. An owner wait that no `wait_for_owner` call continues ends 30 minutes after it started or the latest `wait_for_owner` call returned (`OWNER_WAIT_LIMIT_MS` in `desktop/src/cdp-live/owner-wait.ts`). Bao never ends a wait the agent keeps continuing, so the owner can take as long as he needs, for example to type a code a site emailed. A timer does this, and every `agent_browser` call first checks the limit too, because timers do not run while the Mac sleeps. Either way Bao ends the session as if it were closed: its run finishes `failed` with reason `session_closed`, and the window or task tab closes. The next result gives one line, such as `Bao ended an earlier owner wait from 10:59 PM (run <run_id>); a new open starts a new task.` or `...; nobody continued it for 30 minutes.`

The wait sentence, banner, and instruction name what the page asks, from its title first, then its address: sign in, or clear a human check. A page Bao does not recognize, or one whose title asks to confirm or verify an account or enter a code, gets neutral words: finish the check on the site. Bao never calls such a page a sign-in. The wait time reads in words, such as `waiting 4 min` or `waiting 9 h 53 min`.

Readiness means the tab has an HTTP(S) URL and a nonblank title, its URL or title changed, neither matches a sign-in/check marker, and both stayed stable for 750 milliseconds. This is not proof of authentication. An unchanged URL and title keep waiting even if page content changes. An unrecognized check can use `wait_for_owner` to enter the same private wait; on a Bao-profile session Bao first tries Running Chrome. Metadata does not identify every sign-in form or embedded challenge.

## Pick an engine and profile

The **Settings → Technical details → Page engine** choice remains separate from `agent_browser`. Under **agent-browser (trial)**, saved workflows that explicitly declare `driver: "playwright"`, including supported pass-through tasks, remain searchable and replay through the same browser path as **Current engine (default)**. Other workflows still return `pass-through sessions do not support saved workflow replay`. Historical live workflows remain retired under either choice; see [retirement behavior](cdp-live.md).

Settings → Technical details → Page engine → **Chrome profile** lists existing `Default` and `Profile N` directories under either engine. Chrome's `Local State` supplies display names and account emails. Missing names fall back to the directory name; missing directories are omitted. The saved `chromeProfile` choice selects the source for MCP workflow runs and app **Fresh Chrome copy** and **Running Chrome** runs. Pass-through sessions take the folder from `profile` on the first `open`; the Settings choice is only marked in the list Bao returns when Chrome has several profiles and the open names none. See [Choose the Chrome profile](#choose-the-chrome-profile). App **Bao profile** runs use Login sites instead; see [Workflow reuse](#workflow-reuse).

The copied-profile route reads the selected source and creates a private copy outside the checkout. It does not launch, write to, or lock the source profile. Only the Chrome child gets the real HOME from the passwd entry so it can use the login keychain. The native command process keeps a private HOME. No remote-debugging toggle, Accessibility, Automation, or Screen Recording grant is needed. If a permission prompt appears, stop rather than approving it to keep a test running.

The copy keeps cookies, saved tabs, session-restore files, Session Storage, and encryption metadata. Cache directories are omitted. Chrome starts with sync off and `--restore-last-session`. Bao changes only the copy's exit marker, profile name, theme, avatar, and new-tab background. The profile name is **Bao copy of <original name>**. Its light orange or blue theme differs from the source; its avatar is the origami fox, or penguin when the source already uses the fox. Extensions stay off, including copied themes. These markers do not prove every site's login survives copying.

The copy has mode `0700`. Copying stops after five minutes or 20 GiB. Bao refuses links and active copies. [Session end](#session-end) defines window and copy cleanup. A released keep-open copy or a copy whose Bao process has exited can be reclaimed: Bao stops only Chrome processes using that exact marked directory before deleting it, never the source profile. The 10-minute inactivity backstop does not close a session during an active command or owner wait.

## Known gaps

When the agent's task tab opens two popups before Bao looks, keepTab follows only one: the last fresh tab whose opener is the tab it is already on. Only that followed popup joins the task tabs, so tab lists mark it and finish closes it. The other popup stays open in the owner's Chrome and is not marked. A popup that the followed popup later opens is tracked. A follow-up should track every popup the task tab opened, not only the one the agent followed.

A popup opened from an owner tab the agent switched to stays open and is not marked, because Bao cannot tell that popup from one the owner opened in his own tab.

The handoff sends the window to the Dock and back even when the owner already works in it, for example at a second sign-in wall. Bao cannot tell: the focus emulation the agent's pages get covers every connection to that page, so `document.hasFocus()` reads true for Bao too.

A page that opens a new tab, such as a `target=_blank` link, can still bring Chrome forward: Chrome does that itself, not through the agent's commands. The installed Chrome on macOS does not, until the owner first clicks its window, for example during a handoff. A Chrome that Bao starts directly rather than through LaunchServices, which is the test browser on macOS, always can.

Running Chrome through the Bao extension is gated off. Set `"runningChromeExtension": true` in the Library's `settings.json` to use it instead of remote debugging; no screen offers it. [Running Chrome](extension.md#running-chrome) describes that route. It runs in the Chrome profile where the extension is linked and takes no `profile`.

## Evidence

Each session creates one `kind: "capture"` run in the Library home Bao.app reads. See [Runs and Detailed evidence](v1.md#install-and-run) for the desktop controls that expose commands, screenshots, and native output. The capture receipt remains recording-only, with no replay or teaching actions; a separately saved workflow appears in Workflows. The capture omits Identity and Snapshot inspectors. Durable replay identities and observed effects live in the saved workflow's trail. Capture runs do not claim to count the outside agent's model calls or establish replay green status.

Each step stores its exact command and argv, native stdout/stderr and exit codes, error flag, start/end times, and its sentence (`summary`). Bao saves a pending `open` before startup and updates the run atomically as results arrive. Startup failure produces a failed run with its original error and no invented picture. Uncatchable process termination can leave readable partial runs marked `recording`; handled stops finish the run as described in [Session end](#session-end).

Bao takes a separate page screenshot through CDP on the active tab after each ordinary command, with a three-second deadline. On running Chrome, if that target is not a page, is not http or https, has a `/glic` path, or does not answer a short target lookup, Bao pictures its task tab instead of waiting out the capture. If a capturable active tab then fails to capture, within that capture's own three-second deadline, Bao falls back to the task tab. A copy or Bao-profile session does not fall back to another tab. When Bao keeps the task tab's picture, the tool result says the active tab could not be pictured. A task tab on a sign-in or check page is omitted. When no picture can be kept, the stored error names the cause, except `close`, which records that the session closed and no page remains. A step that ends because Bao's task tab was closed records no picture and no picture error, so the closed-tab sentence stays the cause. The [host contract](mcp-viewer.md#host-contract) names when the tool result includes that cause. Owner handoffs and every `wait_for_owner` call omit page pictures and native screenshot copies. This does not change native refs or screenshot history. Native screenshot files, including relative and default paths, are copied into `shots/runs/<runId>/` before the private state directory disappears. After `close`, the step records the missing page rather than reusing a picture. A recording or screenshot failure logs a warning. Neither changes native command forwarding.

**Raw command arguments, results, and screenshots can contain credentials. This route does not redact them. Do not send data you do not want saved locally.** Saved-workflow input persistence is a separate contract in [permissions](permissions.md#secret-text-in-saved-files).
