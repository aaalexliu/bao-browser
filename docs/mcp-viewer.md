# Read-only MCP run viewer

Bao's local stdio MCP server can show run history and receipts in an MCP Apps host. The desktop app remains a full client. Its Library, Runs, Settings, recording, replay, and human handoffs do not change.

## Host contract

The host must advertise `io.modelcontextprotocol/ui` with `text/html;profile=mcp-app` in its initialize capabilities. Bao then lists and serves `ui://bao/runs/v1.html` through `resources/list` and `resources/read`.

- `agent_browser` shows a card of what the step did in capable hosts, described under [Browser tool cards](#browser-tool-cards). The first `content` block is a plain sentence of the step, quoting the element's own text. Exact native stdout/stderr and snapshot refs follow it; a snapshot with `find` or `diff` gives Bao's shorter view of its stdout, described in [Direct MCP commands](agent-browser-engine.md#direct-mcp-commands). A picture text block follows that output when the step has no page picture or kept a picture of a different tab, unless the step failed to start, the command is `close` or `wait_for_owner`, or the page is owner-private. A thrown error follows. A call rejected before it starts returns only that error. [Wait for owner input in the same session](agent-browser-engine.md#wait-for-owner-input-in-the-same-session) owns that reply. A short `content` block carries `run_id` and `step_id`, so the card works in hosts that forward only `content` and `isError`. When a session ends with a workflow outcome, a final text block carries the save notice described in [Workflow reuse](agent-browser-engine.md#workflow-reuse). `structuredContent` carries only command, status, run and step identity, and optional error metadata, not a second copy of native output.
- `finish_task` content follows [Direct MCP commands](agent-browser-engine.md#direct-mcp-commands). `structuredContent` is a short receipt for the model, with the sentence as `summary`, and not each step's native output. Call `get_run` for the saved receipt. In capable hosts it shows the finished card, and its last `content` block carries `run_id` and `"card":"finish"`.
- `get_run` keeps its existing text receipt and adds a compact viewer in capable hosts.
- `list_runs` adds the viewer to the [catalog history result](bao.md#mcp) and lets the app page through history.
- `inspect_run` reads one run's receipt and workflow steps, twenty steps per page. The host exposes this reader to the app, not the model.
- `open_browser_card` reads one card and its pictures after mount, by run and step, or the finished card by run alone. The host exposes this reader to the app, not the model. [Run evidence](#run-evidence) defines picture limits.
- `open_browser_picture` reads one picture by run, step, and phase without parsing the capture record. The host exposes this reader to the app, not the model.
- `open_step_pictures` reads pictures only after the owner clicks **Open step pictures**. The host exposes this reader to the app, not the model.

Clients that do not negotiate the UI MIME type get the [standard MCP tools and Library identity](bao.md#mcp). These clients get plain text results without viewer metadata or resources and do not need an HTML renderer. This feature does not install or configure Claude Desktop, Codex Desktop, or ChatGPT, and it does not change tool approval settings. Support depends on the host and release; an MCP connection alone does not prove embedded UI support.

The viewer checks host capabilities for further reads, theme, locale, and full-screen mode. **Inspect receipt** requests full-screen mode only when the host offers it. Otherwise the receipt expands inline. The HTML bundles its code and styles and requests no external connections or resources.

Read errors keep the loaded receipt or history visible. For a failed read, try **Refresh**; if it keeps failing, open Bao desktop for local details. If the viewer cannot load, reopen it from the conversation. When the host cannot read more data or does not forward viewer data, use the text receipt or Bao desktop instead. Theme and size updates preserve keyboard focus and the open or closed state of **Workflow steps**.

## Browser tool cards

The same resource renders direct-browser results without changing native commands. Every card leads with one sentence, such as `Clicked "Edit" (button) for "McCabe Organic Coix Seed…"`. Bao builds it from native output, Chrome's own page title and address, and the latest snapshot line for the ref. When the page repeats the element's name and the snapshot tree puts the element inside a list item, row, article, or named group or region, the sentence adds that item's own name. When that item has no name of its own, or a flat `snapshot -i` read or a plain container shows no item, the sentence names only the element. Long names are cut with an ellipsis. The card also cuts a long value the agent typed or opened; the text sentence keeps it whole. Text-only clients get that sentence as the first text block.

| Step | Card |
|---|---|
| open, snapshot, click, fill, press, scroll, tab, screenshot, close | The page picture with the target boxed. Click and fill box the target on the **Before click** or **Before typing** picture. A read boxes the first heading or dialog that no earlier read of that page showed since the last `open`. Other steps show the page after the step. |
| A failed step | The latest earlier picture as **Last seen** and the page after the failure as **Now**, then the native error. The sentence names the step; the native error follows it once. **Last seen** boxes the target only when Bao measured it before the command; an unknown ref gets no box. |
| An owner wait | What the page asks the owner to do, such as sign in or finish the check, with the page title, address, and how long the owner has kept the agent waiting since the handoff started, in words such as **waiting 9 h 53 min**. No picture on the card. [Evidence](agent-browser-engine.md#evidence) owns which screenshot files the run keeps. |
| `finish_task` | The agent's outcome and reason, its optional `done` list, and the step counts and duration. |

Only the box goes on the picture; its label, such as **Clicked**, sits in the caption under the picture after an orange key, so no label covers the page text around the target. A picture of the task tab, kept because the active tab could not be pictured, has no box. The box identifies the action; it does not claim that the site finished its work. Take a later snapshot to check the result.

Visual connections record JPEG page pictures at up to two device pixels per CSS pixel, so a card stays sharp on a Retina display. A picture over the 2 MiB card limit is taken again at CSS-pixel size, then at lower quality. Boxes stay in CSS pixels. Each step stores its sentence and boxes in the run record when it completes, so the card does not depend on stored snapshot text. Hosts can drop `_meta` and `structuredContent` from the tool result; Claude Desktop does. The iframe then reads `run_id` and `step_id` from the `content` block that carries them and calls the app-only `open_browser_card` reader for the card and at most two bounded pictures. Hosts that forward `_meta.baoToolCard` get the card text at once, without image bytes. A step card never falls back to run history. Only `list_runs` and `get_run` read history or a receipt when the host sends no result. The original command output stays intact once, in `content` blocks ordered as described in [Host contract](#host-contract). Tool inspectors belong to the host and may still expose raw data.

The [MCP catalog contract](bao.md#mcp) defines `get_run` text receipts, native-output limits, and links to full output in Bao desktop. The compact viewer uses the separate projection described under [Run evidence](#run-evidence).

**View run** calls Bao's existing read-only `inspect_run` tool with the exact run id. It does not ask the host for filesystem access. The existing receipt body shows capture sessions without requiring a workflow. Recording sessions report recording; finished sessions report their saved result. Capture receipts can open valid bounded step pictures and do not link to a nonexistent workflow. Exact-run inspection pages its output even when the local capture exceeds 2 MiB. It does not apply the history reader's record-size cap. Captures store native output only in step results, not again in console. While a session records, earlier command failures remain step evidence, not a current stop reason or request for human help. Workflow search and description still use their previous presentation.

An unavailable target picture does not prevent the native command. The card names missing evidence instead of guessing a target. Close shows the run's last picture; owner waits and calls without their own picture show no picture. Waits do not take a new screenshot. Early returns keep the active session's run id, except a call rejected before it starts, which names no run. The exception is a command other than a new `open`: when its `run_id` is not the open session, the result carries the named run, not the open session. When that command names no `run_id` while a session is open, it carries no run. An `open` that names a run a newer task ended carries that run and does not touch the open session. [Wait for owner input in the same session](agent-browser-engine.md#wait-for-owner-input-in-the-same-session) owns that reply. Command failures retain their exact diagnostic for the model and give the person a short recovery instruction.

Clients that do not negotiate MCP Apps get the step sentence, then a `Run <run_id>` line, then the native text, then the picture line the [host contract](#host-contract) names when it applies. A sign-in or check wait gives a `Run <run_id> · <outcome>` line and Bao's instruction in words instead, and `finish_task` gives the lines [Direct MCP commands](agent-browser-engine.md#direct-mcp-commands) names. Neither prints JSON: the wait's `outcome`, `instruction`, and `run_id`, and `finish_task`'s short receipt, are in `structuredContent` with the sentence as `summary`. The `Browser:`, `Sign-in import`, and fallback lines are there too, as the `browser` array, on owner waits, `finish_task`, and every result in capable hosts, except a call rejected before it starts. Codex and Claude Code hand the model `structuredContent` in place of the text blocks when a result has it. Test the owner's actual host connection before claiming that host renders the rich card. A local stdio proof does not establish ChatGPT connectivity.

## Run evidence

The viewer reads the same Library files as Bao desktop. It has no second database. Workflow and replay-record reads cap each record at 2 MiB. Exact-run inspection, step-picture reads, and `open_browser_card` load pass-through capture records whole. History pages cap run reads at five records. Detail pages cap run steps and workflow steps at twenty each. Unavailable or oversized history records consume a page slot and show a skipped-record count.

The projection omits the run's input fields, raw snapshots, native command arguments and output, dedicated local asset path fields, video, and resume tokens. Stored reasons and owner requests remain raw and may contain input values or local paths. Only `get_run._meta.baoViewer` and `inspect_run` text and metadata replace read-back values equal to saved secret inputs with `[secret stripped]`. New runs store the executed workflow's secret-input names; an explicit empty list means none. Runs without that field follow current workflow typing, a Known gap. Bao desktop and direct local views keep raw read-backs, and MCP reads do not change signed receipts. It shows model-call counts as unknown when a record does not track them. A recorded zero counts Bao model calls, not calls made by an external coding agent. Browser captures without a saved workflow still have a receipt with their stored step reasons and available pictures. The desktop Command inspector lists recorded commands; [Runs](v1.md#install-and-run) owns that layout. Detailed evidence in Bao desktop also exposes native command arguments and output.

The stored run supplies step reasons, read-back receipts, and owner requests. The current workflow supplies optional labels, not evidence permissions. Editing or deleting a workflow does not hide a past run's evidence. Secret, file, sensitive, and unclassified steps use the same local evidence path as every other recorded step. Marketplace review uploads keep their existing step-crop exclusions. Bao cannot restore values or pictures that an older capture or save discarded.

Receipt pictures load when the owner opens them, not with the initial receipt or history. `open_step_pictures` requires a step recorded in that run, not a current workflow definition. It reads stored or derived filenames within the run's picture directory and returns at most two PNG/JPEG pictures, each capped at 512 KiB for replays or 2 MiB for captures. Browser cards load after mount through `open_browser_card`, which reads the run record and returns at most two pictures, each capped at 2 MiB. These readers send image bytes in tool-result `_meta` for the host app to render. Missing, invalid, linked, or oversized pictures remain unavailable.

The viewer offers no run, resume, edit, approve, or browser-control action. In UI-capable connections, `list_runs`, `inspect_run`, `open_browser_card`, `open_browser_picture`, and `open_step_pictures` are callable by the iframe; other tools are model-only. The host enforces tool visibility. This is not a new authorization scheme or a change to the model's existing tool permissions.

## Known gaps

- Runs without recorded secret-input names use current workflow typing for MCP read-backs. Retyping or removing that workflow can change which saved values the MCP viewer withholds. Runs with recorded names do not use this fallback.

- Clipped capture can reset another CDP client's emulated DPR 2 to 1 on a native-DPR-1 browser. The Retina fixture uses native DPR 2. Firstmate owns the follow-up for cross-client emulation.

- If a host advertises full-screen mode but the request fails, the receipt does not fall back to an expanded inline view. This remains deferred.

## Follow-ups
